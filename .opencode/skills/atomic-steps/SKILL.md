# Атомарная итерация (atomic steps)

Рабочий подход: цель не пишется «целиком», а режется на **атомы** — минимальные
подтверждаемые шаги. Каждый атом — это гипотеза вида «если сделать X, наблюдатель
увидит Y», и он завершается только после наблюдаемого подтверждения на сервере.

## Термины

- **Атом** — минималистичная подтверждаемая гипотеза одного шага к цели. Обязан быть
  **вертикальным срезом**: изменение + способ это наблюдать (E2E-мост/проб) + прогон.
  НЕ «написал метод и надеюсь».
- **Проб (probe/handle)** — «ручка» моста `dmE2EBridge`, дающая наблюдение за одним
  фактом. Существующие: `spawnobj`, `raycast`, `scanbox`, `botdump`. Планируемые (для
  мили): «стойка БЛОК», «был ли получен урон». Без проба атом не подтверждаем → это
  не атом.
- **Критерий успеха** — наблюдаемое утверждение, фиксируется ДО кода (HDD). Не
  «реализован метод», а «при ударе по боту в блоке урон = 0 / < порога».

## Цикл атома

1. **Сформулировать гипотезу** одним предложением: «когда X, наблюдатель увидит Y».
2. **Зафиксировать критерий PASS/FAIL** заранее (что именно увидим в логах/мосте).
3. **Обеспечить наблюдение** (проб/мост + тест-сценарий) — если проба нет, атом =
   `blocked on handle` (в очередь, не в цикл).
4. **Сделать минимальное изменение** (метод/правка), чтобы гипотеза прошла.
5. **Прогнать E2E** (сборка/деплой/сервер/сценарий) — получить PASS/FAIL.
6. **Зафиксировать результат** и выбрать следующий атом (не «дописывать по ходу»).

## Правила (best practice)

- **Одна гипотеза на атом.** Две причины у провала = два атома.
- **Критерий PASS/FAIL (приёмка) — наблюдаемое поведение, а не внутреннее состояние.**
  Проверяй «урон прошёл/нет», а не «флаг m_X == true». Внутреннее — только как
  отладочный лог, не критерий готовности. (Исключение — диагностика бага, см. ниже.)
- **Диагностика бага = принты на ключевых развилках.** Не угадывай причину в голове —
  см. раздел «Диагностика бага (printf debugging)».
- **При зацикливании — шаг назад.** Раз за разом не выходит → сброс по протоколу в
  разделе «Шаг назад (сброс при зацикливании)», а не копание в ту же сторону.
- **Сначала рефакторинг + дымовой тест (walking skeleton), если трогаешь легаси.**
  Перед сменой поведения — characterization-прогон текущего, чтобы рефакторинг ничего
  не сломал. Отдельный атом.
- **Red→Green:** проба/критерий сначала показывает «не работает», потом «работает».
  Если зелёный с первого раза — либо атом не тот, либо нечего было менять.
- **Минимальный срез end-to-end.** Атом, который нельзя собрать и прогнать на сервере
  за один цикл — слишком большой, режь ещё.
- **Атом чист от шума.** В атом входит ТОЛЬКО проверяемая механика; посторонние механики
  (поворот/движение/мозг/FSM), гонящиеся в том же фрейме/контексте, — шум, который сам по
  себе может быть причиной падения атома. Упавший атом чини УБОРКОЙ лишнего из атома
  (свести контекст к минимуму: «стойка + удар» без поворотов/движения), а НЕ добавлением
  гейтов/компенсаций поверх шума.
- **Атом = один коммит** (bump `DM_BOTORAMA_VERSION` на каждое изменение).

## Диагностика бага (printf debugging)

Когда причина неизвестна и «мысленный анализ» уже перепробован — перестать угадывать
и **расставить принты на всех ключевых точках ветвления**. Отладка через принты —
бессмертный паттерн: принт на границе стадий делит пространство причин пополам и не
оставляет багу места скрыться.

Три вопроса, на которые должны ответить принты:

1. **Правильно ли вход инлайнится в модель?** Принт сразу после чтения/анмаршаллинга:
   дамп структуры (глубина, число дочерних элементов на каждом уровне).
2. **Идёт ли алгоритм вглубь иерархии?** Принт в рекурсии/цикле обхода: на каком уровне
   сейчас находимся, что обрабатываем, куда ветвимся.
3. **Не ломается ли алгоритм на самом деле в другом месте?** Принт не только в
   подозреваемом месте, но и вокруг него — баг часто оказывается в соседней стадии.

Правила:
- Принт = лог под DEBUG-доменом (`#ifdef DM_BOT_DEBUG_*` на месте вызова), чтобы не
  зашумлять прод; `Error`-лог — всегда без гейта, если это реально аномалия.
- Сведи вход к минимальному репро (напр. JSON на 2 уровня), чтобы принты читались
  за один взгляд.
- Ставь принты ДО того, как «понял» причину — они должны подтвердить/опровергнуть
  гипотезу, а не оформить уже принятое решение.

## Шаг назад (сброс при зацикливании)

Когда раз за разом ничего не выходит и цепочка рассуждений упирается в бесконечные
итерации внутри **неверно сделанных выводов** — не продолжать копать в ту же сторону,
а сделать шаг назад.

**Триггер «СТОП» (правило трёх попыток).** Если ты три раза меняешь один и тот же модуль,
каждый раз думая «наконец-то переосмыслил и понял, как это работает», а оно в очередной
раз не сработало — это не «нужна ещё одна попытка», это сигнал: твоя модель поведения
этого модуля неверна. Остановись, не меняй код в четвёртый раз.

**Протокол сброса (строго по порядку):**

1. **Забыть всё, что сделал, но помнить ошибки.** Не тащить за собой принятые решения
   и «рабочий» код, но сохранить список ошибок/фактов, которые уже выяснил.
2. **Проанализировать задачу заново** — с чистого листа, без прежних предположений
   о причине.
3. **Сделать ресёрч заново**, закрыв флапающие API наблюдением:
   - Вычленить **флапающие API** — блоки кода/механики, про которые ты думаешь «они
     работают так», а они на самом деле работают иначе (именно они порождают ложные
     гипотезы и зацикливание).
   - Написать **маленькие проверочные автотесты** (characterization-тесты), которые
     чётко показывают **фактическое** поведение этих элементов — не «как должно быть
     по моей модели», а «как есть на самом деле». Один флапающий API — один микро-тест
     с наблюдаемым результатом.
   - Перечитать API/доки/референсы свежим взглядом, не через призму старой гипотезы.
4. **Построить план заново** — на базе **проверенной** гипотезы (фактическое поведение,
   а не предположение), с учётом помненных ошибок (они — вход, а не вывод).
5. **Вспомнить, что уже сделано, и проверить корреляцию**: где новый план пересекается
   со старым, где расходится. Расхождение — сигнал, что старая ветка была ложной;
   пересечение — что часть работы можно переиспользовать, а не выбросить.

Связь с атомами: сброс — это не «сдаться», а пере-декомпозиция. Первый атом после
сброса — чаще всего диагностический (принты на границе стадий или characterization-тест
флапающего API), чтобы новым наблюдением подтвердить, что прежняя гипотеза была ложной.

## Анти-паттерны

- Атом «написать метод» без проба/критерия (нет подтверждаемости).
- Гипотеза без фиксированного критерия успеха (тогда PASS/FAIL субъективен).
- Несколько гипотез в одном атоме (непонятно, что именно провалилось).
- Прогон «в голове» вместо E2E на сервере (скрытая зависимость от окружения).
- Рефакторинг и смена поведения в одном атоме без дымового прогона до.
- Зацикливание: повторять одни и те же «исправления» без наблюдаемого сдвига вместо
  шага назад (см. «Шаг назад (сброс при зацикливании)»).
- Подмешивать посторонние механики (поворот/движение/мозг/FSM) в атом «проверь X» — шум,
  ломающий чистоту атома.
- Лечить падение атома добавлением гейтов/компенсаций (адресуя симптом), вместо уборки
  лишних механик из атома (адресуя причину).

## Роли в botorama

- `dayz-research` выписывает гипотезы `[нужно проверить]` с конкретным эмпирическим
  вопросом → оркестратор режет их на атомы.
- `dayz-dev` делает атом: код + тест-сценарий + список релевантных доменов; если нужен
  проб — расширяет `dmE2EBridge` батчем (не на лету).
- `dayz-tester` гоняет атом как «частичный» тест, отчёт PASS/FAIL + что увидел в логах.
- `dayz-reviewer` — по триггеру (нетривиальное изменение), но не блокирует сам атом.
- Бюджет итераций на атом — по `AGENTS.md` («Координация субагентов», п.6): ≤3
  rework/delegate-цикла, иначе стоп + отчёт (анти-бесконечный цикл).

## Шаблон атома (тикет)

```
Атом: <одна гипотеза>
Гипотеза: когда <условие>, наблюдатель увидит <факт>.
PASS: <что в логах/мосте = успех>
FAIL: <что = провал>
Проб/мост: <spawnobj/raycast/scanbox/botdump/…> (нет → blocked on handle)
Сценарий: <шаги тестировщика: спавн бота → ... → наблюдатель бьёт → фикс урона>
Изменение: <файлы/метод>
Критерий готовности: PASS на сервере + ревью при нетривиальности.
```

## Пример (блок, как задумано)

```
Атом: бот умеет ставить блок.
Гипотеза: когда бот в стойке БЛОК и по нему бьют спереди, урон не проходит.
PASS: мост фиксирует урон = 0 (или ниже порога) при ударе по блоку.
FAIL: урон проходит как без блока.
Проб/мост: «стойка БЛОК» + «фиксация полученного урона» в dmE2EBridge.
Сценарий: спавн бота → лицом друг к другу → бот в БЛОК → наблюдатель бьёт → читаем урон.
Изменение: SetMeleeBlock/SetBlock + вызов из fight-logic (raised-флаг).
```

Первым, скорее всего, идёт не блок, а дымовой/рефакторинг-атом (проверить, что текущий
ERECT-удар вообще наносит урон и не крутит модель) — чтобы был baseline перед переписыванием.
