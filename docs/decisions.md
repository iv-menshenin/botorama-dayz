# Журнал решений (decision journal)

Краткая выжимка **существенных развилок и принятых решений** — чтобы субагенты не
выводили одно и то же решение заново в каждом новом контексте. Это НЕ список ошибок
(ошибки — в `codeguide.md`/скилле по классификации из AGENTS.md) и НЕ факты API
(они — в `docs/research/*.md`). Здесь — **решения и почему они приняты**.

## Правила ведения

1. **Субагент предлагает, оркестратор фильтрует.** Субагент в отчёте перечисляет
   существенные развилки и принятые решения; оркестратор при ревью решает, что сюда
   попадает, и держит документ узким.
2. **Формат записи** — три строки, без воды:

   ```markdown
   ### <домен>: <решение одним предложением>
   Решение: <что решили>
   Почему:  <контекст/развилка и чем кончилось рассуждение>
   Действует пока: <условия применимости — когда решение НЕ действует>
   ```

3. **Кап ~15–20 записей.** Добавил новую — слей с дубликатом или удали наименее
   существенную. Оркестратор проверяет кап при каждом commit.
4. **«Действует пока» — обязательно.** Запись без условий применимости превращается в
   догму (якорение): будущий агент применит старое решение в новом контексте. Если
   условий нет — запись не нужна.
5. **Существенность.** Только развилки, где агент реально колебался и где выбор влияет
   на код/тесты. Тривиальные решения не записывать.

### e2e: транспорт сценариев — файлы, а не HTTP
Решение: агент общается с тест-сервером через файловый канал
`$profile:dmBotorama/e2e/` (`in/` → `out/` + `done/`).
Почему: файл — природная транзакция (`.tmp` → `rename` = атомарность), нет
процесса-сервиса, результат лежит рядом с логом сервера.
Действует пока: нет второго рантайма/потребности в live-опросах и стриминге событий.

### defines: event vs per-frame домены и режимы сборки
Решение: `build.sh` в трёх режимах — `--prod` (только `DM_BOT_PROFILE`), дефолт
(функциональный, defines как закоммитил dev), `--test` (все event-домены из
`tools/defines_test.txt`). Per-frame домены (`DM_BOT_TRACE_LOOK`,
`DM_BOT_DEBUG_PERFRAME_MOVING_LOG`) в `--test` не входят.
Почему: регрессия должна покрывать все event-домены, а per-frame спамит на каждый
кадр и убивает overload-тесты.
Действует пока: per-frame домен не нужен конкретному сценарию (тогда dev включает его
точечно в defines[]).

### API: QueryFlags/CollisionFlags — последовательные enum'ы, не битмаски
Решение: комбинировать флаги через `|` нельзя; статику и динамику в бокс-скане брать
двумя отдельными вызовами (`QueryFlags.DYNAMIC` + `QueryFlags.STATIC`).
Почему: `QueryFlags` = `NONE=0, STATIC=1, DYNAMIC=2, ORIGIN_DISTANCE=3, ONLY_ROADWAYS=4`
— `STATIC|DYNAMIC` = `1|2 = 3 = ORIGIN_DISTANCE` (чужой член). Плюс `|` запрещён
codeguide. `CollisionFlags.ALLOBJECTS` — отдельный член enum'а для «все объекты по лучу».
Действует пока: API не изменится и не появится нативная битмаска флагов.

### e2e: мировые координаты в Op — Y=0 означает «авто-земля»
Решение: для любого мирового поля (`Pos`/`From`/`To`/`Min`/`Max`) `Y==0` (или поле не
передано) → `SnapToGroundExactly(p)`; `Y!=0` → явная высота как есть. Для `raycast`
дополнительно +`DM_E2E_EYE_HEIGHT` (высота глаз) при `Y==0`.
Почему: сценарии не могут знать уровень земли заранее; хардкод абсолютного Y ведёт к
боксам/точкам «под землёй» (scanbox давал `0 entities` с Y=-5..5 при земле ~339).
Действует пока: не появится поле с относительной высотой (напр. `YRel`) или иной
способ указать «земля ± дельта».

### API: AI-выжившие «загрязняют» dmEntityRegistry.GetPlayers()
Решение: `dmEntityRegistry.GetPlayers()` содержит И AI-выживших, И людей (потому что
`dmAISurvivorBase : PlayerBase`, а `modded PlayerBase` регистрирует каждую сущность).
Чтобы найти человека — фильтровать `dmAISurvivorBase.Cast(p) == null` (человек — ванильный
`PlayerBase`, не наследник `dmAISurvivorBase`).
Почему: `observe` телепортировал первого AI-бота (~88 settlement-ботов) вместо человека.
Влияет на любой код, читающий `GetPlayers()` как «людей».
Действует пока: не будет отдельного реестра «только людей» или флага `IsHuman` в `PlayerBase`.

### navigation: дерево детектить райкастом IsTree(), а не через navmesh-запрос
Решение: «здесь дерево» узнаётся по объекту из райкаста — `hit.obj.IsTree()`/`IsBush()`
(виртуальный метод `Object`, `TreeHard`/`TreeSoft`; класса `TreeBase` нет). Для ствола —
`type = ObjIntersectGeom` (физика), НЕ `ObjIntersectView` (листва даёт ложные срабатывания).
Почему: point-query типа navmesh-площади в API нет (`PGAreaType.TREE` — только вес пути
через `SetCost`), поэтому «дерево под точкой» не запросить напрямую.
Действует пока: не появится нативный `GetPolyFlags`/area-query под точкой; или не подтвердится
эмпирически, что view-луч на нужной высоте не цепляет листву.

### melee: спавн зомби для теста — CreateObject(..., init_ai=true), не InitAIAgent(AIGroup)
Решение: в E2E-спавне зомби передавать 4-й аргумент `CreateObject(type, pos, false, true)`
(`init_ai=true`) — иначе зомби «без мозга» (не ходит, не атакует). Так делает Expansion
(`RPC_SpawnZombie`) и ванильный дебаг-плагин.
Почему: `DayZCreatureAI.InitAIAgent(AIGroup)` требует `AIGroup`, чей конструктор приватный —
из скрипта группу не создать.
Действует пока: не появится сценарий «дозасспавнить мозг уже созданному зомби».

### melee: кручение при ударе — глушить HeadingModel для MELEE2 (как и для MOVE)
Решение: ванильный `HeadingModel` для MELEE2 падает в `RotateOrient` (крутит корпус) — наш
override глушил его только для `COMMANDID_MOVE`. Расширили лок на `COMMANDID_MELEE2` + пропуск
`ApplyBodyTurn` во время удара.
Почему: бот делал полный оборот за замах (spin 308°), корпус разворачивался от цели → проверка
угла в `HitTo` отсекала удары → «бегающий болван» (stall).
Действует пока: не исчерпан остаточный спин (~267°, редкий 1/288 ударов) — по эмпирике он от
самой MELEE2-анимации (root motion), а не от HeadingModel/ApplyBodyTurn (см. techdebt).

### body: «настоящий» нокаут/связывание — точечные правки, а не action-manager
Решение: чинить нокаут/связывание/развязывание точечно (`m_IsUnconscious` + серверный дроп +
modded `CanBeRestrained()` + свой restrainer-хук), а НЕ давать боту action-manager (как
Expansion `eAIActionManager`).
Почему: action-manager — крупный архитектурный сдвиг (и заодно чинит CPR/лут/связать), но
рискован и избыточен для текущего скоупа; CPR/лут гейтятся только `IsUnconscious()` (net-var),
а связывание — `CanBeRestrained()` (`GetActionManager()!=null`), что закрывается точечно.
Действует пока: не появится потребность в массовых ванильных action'ах для бота (тогда
пересмотреть в пользу action-manager).

### drive: тяга — нативный привод (передачи + газ), не импульс
Решение: машину движет нативная МКПП: `ShiftTo(CarGear.FIRST/SECOND/THIRD/FOURTH)` по
скорости + `SetThrottle` (через `modded CarScript.OnInput`). Импульсный толчок
(`dBodyApplyImpulseAt`) НЕ используется.
Почему: ранний вывод «сцепление не замыкается → нативная коробка не едет, нужен импульс»
оказался МИСКЕЙЗОМ — он был сделан на машине с ТРЕМЯ колёсами (баг `spawncar`). После
фикса колёс (4/4) нативная коробка работает: разгон 0→47 км/ч, передачи 2→3→4→5,
RPM реалистичный (idle 900 → круиз ~1500, без красной зоны). Эталон — Expansion AI
(`ShiftTo(CarGear.FIRST)` + `SetThrottle`).
Действует пока: машина на 4 колёсах. (Импульс может понадобиться как аварийный «вытащить
из ямы», но не как основная тяга.)

### drive: нативные сеттеры ввода работают только в Transport.OnInput
Решение: `SetThrottle/SetBrake/SetSteering` применяются в `override Transport.OnInput(float dt)`
(через `modded class CarScript` + поля `dm_Drive*`), а НЕ из `OnUpdate` интента.
Почему: `OnInput` — штатный хук «после input simulation step» (research `vehicles.md`); из
`OnUpdate` сеттеры мёртвые (`SetThrottle(0.6)` не поднимал `EngineGetRPM()`, держал idle 900).
Эмпирически подтверждено: через `OnInput` rpm растёт 900→1807.
Действует пока: не появится подтверждённый способ гнать ввод из другого хука.

### drive: дорожный путь по navmesh ROADWAY фрагментирован — fallback на пеший
Решение: дорожный маршрут (`PGFilter` с `SetCost(ROADWAY,1)/TERRAIN,10000`) часто усечён
(последний вейпоинт далеко от цели — ROADWAY-навмеш не связен); при усечении интент
фолбэкается на пеший `FindPathTo` (TODO-костыль).
Почему: в навмеше дороги размечены фрагментарно; Expansion для ИИ-вождения строит
СОБСТВЕННЫЙ граф дорог (`eAIRoadNetwork`) из road-объектов (`ObjectIsRoad`), а не navmesh-ROADWAY.
Действует пока: не портирован road-graph по образцу Expansion `eAIRoadNetwork` (крупная задача).

### drive: знак руля — `SetSteering` и `Atan2(cross,dot)` имеют ПРОТИВОПОЛОЖНЫЕ знаки
Решение: `steerTarget = -angle / 1.57` (минус), где `angle = Atan2(cross, dot)`,
`cross = carDir.x·toDirZ − carDir.z·toDirX`.
Почему: телеметрия `DRIVE-TELE` показала положительную обратную связь — `angle>0`
(цель СЛЕВА от курса) давал `steer>0` (поворот ВПРАВО), машина отворачивалась от цели
и уходила в спираль ±π (главная причина осцилляции/«дёрганья»). `SetSteering(+)=вправо`,
`Atan2(cross,dot)(+)=цель слева` — знаки противоположны (эталон Expansion использует
`Math3D.AngleFromPosition`, знак которой совпадает с `SetSteering`).
Действует пока: используется нативный `SetSteering` и этот расчёт угла; при смене
конвенции угла (напр. на `AngleFromPosition`) минус убрать.

### drive: руление — только нативный SetSteering, без бокового импульса
Решение: поворот делает только нативный `SetSteering` (через `dm_DriveSteering` в
`CarScript.OnInput`); боковой импульс `ApplySideImpulse` (lateral `dBodyApplyImpulseAt`
на носу) удалён.
Почему: боковой импульс был костылём «доворачивать» при импульсной тяге; при нативном
приводе он лишний, а на грунте (низкое сцепление) толкал кузов ПОПЕРЁК — машина скользила
вдоль своей оси вместо разворота корпусом (наблюдение человека-наблюдателя).
Действует пока: нативный `SetSteering` достаточен для поворота; импульс можно вернуть как
аварийный «вытащить из ямы», но не как руление.

### drive: канал DRIVE — без default-rest
Решение: в арбитраже `dmBotIntentsChannel.DRIVE` сбрасывается в null, но БЕЗ «покоя» (как
LOOK/MOVE/STANCE), в отличие от остальных каналов.
Почему: канал монопольно пишет только интент вождения; возврат мобильности — ответственность
graceful-exit самого интента (`StopCar` + `GetOutVehicle`), а не арбитражного сброса.
Действует пока: не появится второй интент на DRIVE или потребность в «нейтральном» газе/руле.

### merge: ключ дедупа рёбер — строковый `min:max`, не int-hash
Решение: дедуп рёбер в `SewNodes` — через `map<string,bool>` с ключом
`lo.ToString()+":"+hi.ToString()` (lo/hi = min/max(From,To)), а не `f*100000+t`.
Почему: int в Enfusion 32-битный; `44k*100000 ≈ 4.4e9` переполняет (max ~2.1e9) → коллизии/
отрицательные ключи. Строковый ключ — биекция Python-кортежа `(min(f,t), max(f,t))` из
`merge_road_tiles.py`, надёжен на любом размере графа.
Действует пока: число узлов больше ~21k (порог переполнения `n*100000`); на малых графах int-hash
тоже корректен, но строковый не дороже — поэтому держим строковый везде.

### roads: перенумерация Id узлов — в билдере (источник), не в склейке (потребитель)
Решение: дыры в Id узлов чиню перенумерацией в конце `BuildGraph` (`RenumberContiguous`),
а не подстройкой `AppendTile`/`SewNodes` под дыры.
Почему: склейка (и Python `merge_road_tiles.py`, и Enfusion) держит инвариант `Id == индекс массива`
(`nodeOffset = Count()`, `SewNodes` индексирует `parent` по `edge.From`). Чинить в двух потребителях
дороже и хрупче, чем устранить причину один раз в билдере.
Действует пока: билдер — единственный источник тайловых графов; если появится второй генератор
графов — перенести инвариант контигуальности в его контракт.

### roads: упрощённый граф — производная полного графа с провинансом (не отдельный артефакт)
Решение: `simplified_graph.json` получается только детерминированным прогоном
`tools/simplify_road_graph.py` из `road_graph.json`; вершины несут `Members`, рёбра — `Path`
(ссылки на Id полного графа).
Почему: аппрув «рваной» дороги тестировщиком применяется к полному графу, а упрощённый
пересчитывается — иначе два графа рассинхронизируются. Провинанс делает соответствие аудируемым.
Действует пока: полный граф — единственный источник; ручная правка упрощённого запрещена
(любое изменение — только через полный граф + пересчёт).

### drive: детект препятствий — `ObjIntersectGeom` на горизонтали высоты корпуса
Решение: райкаст объезда вперёд — `RaycastRVParams.type = ObjIntersectGeom`, луч на высоте
корпуса машины (`carPos[1]`), горизонтальный.
Почему: дефолтный `ObjIntersectView` даёт ложные хиты по листве/LOD (research navigation.md);
`Geom` — физическая геометрия (обломки/баррикады по коллизии). Высота корпуса, а не земли.
Террейн/вода приходят как `hit.obj == null` и отфильтровываются в `RaycastHits` (земля — не
препятствие); кусты — `IsBush()` и тоже пропускаются. `groundOnly=false` означает «рейкастить
ВСЁ, включая землю» (не «террейн не ловится», как ошибочно писали раньше).
Действует пока: детект статических препятствий на дороге; детект глубокой воды — отдельно
(`CollisionFlags.ONLYWATER`), объездной райкаст её сознательно не ловит.

### move: троттл «нет пути» — статик-кэш, ключ = тип + цель
Решение: always-on `MoveTo: нет пути …` (и recovery/detour/stuck) троттлится раз в 30 с на ключ
`тип_сообщения + m_Goal` через **статический** `map<string,float>`.
Почему: settlement-боты зациклены на недостижимые точки и пересоздают `MoveTo` каждый ретрай →
спам в лог. Instance-поле обнулялось бы при каждом `new`, поэтому кэш статический (переживает
пересоздание интента); ключ «тип+цель» — разные ветки/голы логируются независимо.
Действует пока: одна недостижимая точка у одного бота; если ботов много и у всех разные голы —
троттл на ключ не урежет общий объём (тогда глушить на уровне спавн-менеджера).

### drive: детект baked-static препятствий в сотах — ObjIntersectGeom (не Fire) + фильтр не-блокирующих объектов
Решение: детектор сот бьёт тонкими лучами с `type = ObjIntersectGeom`; препятствие = `hit.obj != null`
(физическая коллизия); одежда (`IsClothing()`) и `DeployableContainer_Base` (бочки/рюкзаки)
пропускаются; сканбокс `ScanEntities` удалён.
Почему: `ObjIntersectFire` не возвращал `Static_rock_monolith` (`RockBase : Object`, минный камень без
fire-геометрии) на тонких лучах, тогда как `Geom` бьёт его — хит приходит «пустым» (`obj` не-null с
`GetType()==""`, `parent==null`, `surf==null`). «Фантомные хиты» оказались багом обрезки чат-команд
заказчика, а не нативным поведением — «чистка» по `pos∈отрезок` была ложным решением и удалена.
Действует пока: детект статических/baked-static препятствий; мелкий лут (одежда/бочки) сознательно
НЕ блокирует (не препятствие для проезда).

### drive: геометрия детектора сот — гексагон radius 0.5 + косые лучи 0.5→0.2
Решение: веер из 3 диагоналей гексагона (A→D/B→E/C→F) + вертикаль в O, тонкие лучи;
`DM_GRID_HEX_RADIUS = 0.5`; горизонтальные лучи «косые» — beg на 0.5 м, end на 0.2 м.
Почему: косой луч захватывает «висячие» объекты (подвешены выше 0.2 м); радиус 0.5 даёт плотное
покрытие без дыр на монолите (0.33 «мельчил» из-за погони за барьером; когда барьер пойман — можно
укрупнить ячейку и сэкономить ресурсы скана).
Действует пока: покрытие удовлетворительное (подтверждено E2E-рендером); на замерах
производительности радиус может быть пересмотрен.

### drive: pathfinding сот — центральная линия вместо A*/BFS
Решение: A*/BFS удалены целиком; маршрут объезда строит «эффективный центр дорожного
полотна» — для каждого ряда walkable (GREEN/SAFE) интервалы → выбранный интервал →
колонка шагает к его середине на ±1/ряд (связный hex-путь), при блокировке шага — прыжок
к середине интервала; затем string-pulling.
Почему: заказчик просил «waypoint стремился к эффективному центру полотна» (середина зелёной
части при перекрытой левой). A* с равномерной стоимостью давал произвольный кратчайший путь
(жмётся к краю препятствия, а не к середине коридора). Центральная линия — прямой
«человеческий» ответ (меряем свободный коридор → идём в его середину). ±1/ряд = связный
hex-путь и «стремление» (не резкий снап); фолбэк-прыжок закрывает торцевую грань барьера
(разрыв шире 1 соты), а `SmoothPath` валидирует отрезки прыжка.
Действует пока: территория — узкая forward-полоса (обочина 3 м), препятствия — продольные
частично-перекрывающие барьеры. Для строго перпендикулярной стены в узкой полосе (прыжок
пересекает RED) центральная линия может дать невалидный отрезок — нужна маршрутизация
вокруг торца/расширение территории (см. techdebt J3). (Заменено v3.279 слоёным графом — см.
следующую запись.)

### roads: pathfinding сот — слоёный граф вместо центральной линии
Решение: центральная линия заменена на слоёный граф: зелёные = SAFE-клетки, по каждому ряду —
«зелёные середины» (центры SAFE-интервалов), рёбра только вперёд между соседними рядами с
валидацией «не пересекает RED» (`SegmentCrossesRed`), вес = XZ-длина; кратчайший путь — DP по
слоям; затем string-pulling (дедуп) до точек поворота (коллинеарные/одинаковые клетки соседних
рядов схлопываются).
Почему: центральная линия была хрупкой: фолбэк-прыжок через торцевую грань барьера мог дать
невалидный отрезок через RED (techdebt J3), а жадный выбор интервала «содержащий prevCol»
застревал на диагональных барьерах. Граф с рёберной валидацией + глобальным кратчайшим путём
закрывает класс задач одним механизмом (меряем проходимость → ищем путь). String-pulling в конце
нужен, т.к. на doubled-гекс-сетке середина коридора прямой дороги чередует колонки 0/±1 между
рядами (чётность) — буквально «одна и та же клетка» в соседних рядах не встречается, поэтому
дедуп реализован как схлопывание коллинеарных точек (заодно сжимает путь).
Действует пока: территория — forward-полоса 2× ширины дороги, рёбра только вперёд (по рядам).
Для стены поперёк всей полосы путь не найдётся (нет поперечных/обратных рёбер) → FAIL;
расширение территории/маршрутизация вокруг торца — отдельная задача (см. techdebt J3).

### e2e: drivetest — монолитный судья вождения (v3.282)
Решение: проверка «бот сел → объехал → доехал» реализована одним deferred-op `drivetest`
(фазовая машина PREP→TEST) с немедленным абортом job'а, а не набором `wait`/`assert`.
Почему: спека требует «прекращается немедленно» при нарушении guard'а (интент жив,
`CrewMember(DRIVER)==бот`, средняя скорость за окно >0, мотор on/rpm>idle) и выделенный
таймаут посадки 45с — это кросс-тиковое состояние (фаза, 30-с окно скорости), которое
нельзя собрать из stateless-шагов автомата. Монолит держит это состояние в одном месте.
Действует пока: функциональный код вождения/посадки не тронут (харнесс только наблюдает
через публичные API); сама посадка — отдельный открытый баг (см. techdebt J3).

### e2e: drivetest — «сел» = член экипажа И !get-in анимация (v3.282)
Решение: переход PREP→TEST требует `CrewMember(DRIVER)==pawn && !IsGettingIn()`, а не
только `CrewMember==pawn`.
Почему: эмпирически (прогон) `CrewMember(DRIVER)` кратковременно возвращает `==pawn` в
момент get-in анимации, хотя фактическое членство не устанавливается (`crew=false`
стабильно) — без дебаунса харнесс давал ложный `driver lost` вместо честного
`seating timeout` при баге посадки.
Действует пока: посадка чинится отдельно; после фикса это условие должно перестать
срабатывать на транзиенте (стабильное `crew=true`).

### e2e: drivetest — reach-first PASS поверх guard'ов (v3.282)
Решение: в TEST-фазе достижение выхода (`carpos` в `Tolerance`) проверяется ДО всех
guard'ов и сразу даёт PASS.
Почему: на успешном финише Drive-интент штатно завершается (удаляется из пула → «интент
Fail/removed»), мотор глохнет → «engine off», скорость →0 → «stop-guard». Без reach-first
харнесс абортил бы успешное прибытие ложным guard'ом. Достижение выхода — терминальный
успех, приоритетнее любых guard'ов.
Действует пока: семантика PASS — «доехал до точки выхода», guard'ы — только про путь к ней.
