Статус: черновик к обсуждению. Источник правил лута — `docs/looting.md`
(единый источник правды; черновик — `docs/looting-and-exploration.md`). Факты —

## ✅ Баги выживания (3 шт) — РЕШЕНО (v3.405)

- **Еда бесконечно (Quantity=0)**. `PhaseEat` при `qty<=0` вызывает `SetQuantity(0)` (конфиг
  `varQuantityDestroyOnMin`: еда/сода → `Delete()`, бутылка → остаётся пустой); `FindEdible` фильтрует
  `qty<=0 && IsOpen()` (пустую бутылку пропускает, запечатанную консерву находит для вскрытия);
  анимация поедания гасится (`StopAnim` до `SetQuantity(0)`). E2E: еда удаляется, бутылка пустая, нет цикла.
- **Удаляет предметы из рук / бегает с предметом**. `FreeHands()`: поиск MELEE→SHOULDER→Backpack_1,
  мув туда (обёртка `RemoteObjectTreeDelete/Create`, без clone+delete); таймаут держания 1 мин (пауза в
  бою). Fighting-экипировка: FreeHands предпочтительно, `PLACEONGROUND` — фолбэк. E2E: топор из рук → слот, не дропнут.
- **Таблетки/витамины/настойка = еда**. `GetCategory`: `IsMedical` до `Edible_Base`; `FindEdible` скип
  `IsMedical`; `IsMedical` дополнен `IodineTincture`/`DisinfectantAlcohol`/`PurificationTablets`/`ChelatingTablets`.
  E2E: медицина не естся, естся только настоящая еда.

## ✅ Полный отказ от clone+delete — РЕШЕНО (v3.405)

Правило «НИКОГДА clone+delete, только Tree(Delete/Create)» зафиксировано в `docs/codeguide.md`/
`docs/decisions.md`/`docs/research/body-drop.md`. `DropItemToGround` (HANDS→GROUND) переписан на
`item.LocalTakeToDst` (синхронный `LocationSyncMoveEntity` — работает на мёртвом/нокаутированном, где
`Man.LocalDropEntity` давал deferred `HandEventDrop` и рассинхрон клиента).

## ✅ 1. Арбитраж NONE-интентов (EatDrink мёртв) — РЕШЕНО (v3.373)

- **Факт**: `dmBotIntent_EatDrink` и `dmBotIntent_TidyInventory` оба `IDLE + PARALLEL +
  m_Manage = NONE`. Арбитраж трактовал `NONE` как однопобедный канал → TidyInventory
  (первым в Spawn) выигрывал каждый тик, EatDrink получал `OnSkip()` (no-op) →
  `EatDrink.OnUpdate` не вызывался никогда.
- **Решение (простое, как договорились)**: ротация с залипанием.
  - `dmBotIntent`: поле `m_LastRun` + метод `IsBusy()` (дефолт false).
  - `EatDrink.IsBusy()` = `m_Phase != 0` (занят при открытии/поедании).
  - `dmAISurvivor.IntentsArbitrationNone`: среди NONE-интентов побеждает тот, у кого
    `m_LastRun` минимален; занятый держит канал (не обновляет m_LastRun), не-занятый
    уступает (`m_LastRun = now`). 100% перебор всех конкурентов.
  - Боевой гейт прежний (интент-уровень `IsInCombat → StopAnim + phase=0`), при этом
    сброс фазы делает `IsBusy=false` → лач отпускается сам.
- **Проверено Red→Green** (`surv-food-1b`): energy 200→324 (съел), консерва `_Opened`,
  `[EatDrink]` в RPT; Red — energy 200→194, `[EatDrink]` ноль.
- **Отложено (не в этом атоме)**: вынос еды/питья в состояние заботы о здоровье — это
  отдельная, более крупная переработка; пока хватает ротации (см. «Обсуждение №1»).

## ✅ 2. Ранжирование `dmRequirements` — РЕШЕНО (v3.390)

- **Принцип**: ранжирование — ТОЛЬКО карго; одежда/оружие/слоты — другой путь.
- **Перечисление**: `dmLoot.CollectCargoRecursive` (вариант B, только карго; надетое/аттачи вне ранга).
- **Сортировка по качеству** (`GetQuantityNormalized()+GetHealth01()`, убыв.) до раздачи индекса.
- **Пер-категорийный decay** (`index = baseIndex * decay^(n-1)`, `n` — позиция в своей группе):
  свой патрон/магазин 0.95, чужой 0.85, еда/вода 0.75, ремонт 0.70, прочее 0.50 (константы
  `DM_LOOT_DECAY_*`).
- **Калибровый матч** через `dmArsenal.HasWeaponForCaliber` (резолв `dmWeaponRange.GetBulletFromMagazine`).
- **Проверено Red→Green**: свой 762x54 #2=0.95, чужой 12ga #2=0.85.

**Отложено (follow-up, не блокер ядра):**
- Классификация `Ammo_762x54` → MAGAZINE (`IsMagazine()` раньше `IsAmmoPile()`; `Magazine` typedef
  покрывает пачку) — дедуп пачек с магазинами. Проверить семантику перед отдельным фиксом.
- `AmmoBox_*_20Rnd` → AMMO (сейчас OTHER; калибр из конфига `Resources`).
- `DebugRankDump` не различает однотипные предметы (нет quantity) — удобство наблюдения.

## ✅ 3. Эвакуация — единый детерминированный репак (не наивный drop-1) — РЕШЕНО (v3.393)

- **Как решено**: корень осцилляции был в дропе — `DropItemToGround` делал clone+delete
  (сущность менялась → re-collect/игнор по удалённому оригиналу no-op). `DropItem` теперь
  ветвится: не-руки → ванильный `LocalDropEntity` (сущность та же, слот карго освобождается
  синхронно), из рук → clone+delete. E2E: консерва легла, патроны вернулись, осцилляции нет
  (см. `docs/research/drop-to-ground.md` §3.2/§4, `docs/decisions.md` «дроп не-рук»).
- **Спека** (`looting.md` §Эвакуация-репак): `GetDiscardOrder()` → выложить всё фреймами
  → новая вещь в конец → собрать с конца (новая → нужное → ненужное) → не влезло → игнор.
  Явный массив + сортировка по убыванию желаемости (детерминизм).
- **Код**: полный репак уже есть (`dmBotIntent_PickUp.Evacuate`), но в пути подбора
  еды/патронов работает другой путь — `EnsureCarry → EvacuateForItem`, который сбрасывает
  **1** предмет (1 ячейка) и при неудаче сразу «нет места → игнор».
- **Следствие**: консерва 2×2 (4 ячейки) не влезает после drop-1 → бот сдаётся (food-1c).
- **Направление**: вести food/ammo/other через полный `Evacuate`; убрать/переписать
  наивный `EvacuateForItem`. На время операции — стоять/присесть (тот самый
  «присесть-отдохнуть» из #72).
- **Арсенал-семантика — РЕШЕНО (v3.394)**: дроп тихий (без `Unregister`), постоянная отбраковка —
  через игнор-лист. `DropItem` больше не зовёт `Unregister`; введён `dmAISurvivor.Discard(item)` =
  `Wishlist.Ignore(item)` + `Arsenal.Unregister(item)` (заменил 7 call-sites `Wishlist.Ignore` в
  луте/репаке). Лефтовер репака вычитается через `IgnoreLeftovers → Discard`. Для тестов —
  `dmArsenal.ForceRescan()` (публичный) + e2e-оп `rescanarsenal` (принудительный рескан после
  loadout, т.к. loadout создаёт предметы мимо `Register`). E2E PASS: дроп при репаке тихий (нет
  `[Arsenal] Unregister` от `DropItem`), лефтовер вычитается, `rescanarsenal` работает.

## ✅ 4. Игнор выброшенного (анти-осцилляция) — РЕШЕНО (v3.393)

- **Как решено**: тот же фикс, что в №3 — локальный мув оставляет сущность той же, поэтому
  `Ignore(item)` в `IgnoreLeftovers` работает по ссылке на реально выложенный предмет (а не
  по удалённому клон-оригиналу). E2E: выложенные патроны `ignored=true`, повторного подбора нет.
- **Спека** (`looting.md` §Wishlist + §Эвакуация): «вещь не влезла → игнор-лист»;
  выброшенное → `Ignore` (авто-Unignore ~5 мин).
- **Код**: `IgnoreLeftovers` есть в `PickUp.Evacuate`, но осцилляция показывает, что
  выброшенное подбирается обратно. Нужно убедиться, что `Ignore` покрывает оба пути
  (и `EvacuateForItem`), и не снимается раньше времени.

## 🟡 5. Расход медицины — НЕ баг (снято)

- Расход уменьшает **quantity**, а не удаляет предмет. «Предмет не расходуется» — ложная
  тревога (`invdump` не показывает quantity). Снять; при желании — добавить quantity в
  `invdump`.

## ✅ Ресёрч+тест: перечисление инвентаря (spike) — ВЫБРАН вариант B

- **«Главного карго» пешки НЕТ.** `pawn.GetInventory().GetCargo() == null`; loose-предметы в
  карго контейнера или в руках. → в `dmRequirements.ComputeUsedRatio` первый
  `AccumulateCargo(inv.GetCargo())` — мёртвый no-op (почистить в №2).
- **Выбран вариант B** — ручная рекурсия `GetCargo().GetItem()` + `FindAttachment()`
  (карго→дропаемое+спуск, слоты→только спуск); спускается во вложенные контейнеры (проверено
  `SmallProtectorCase`). Вариант A (`EnumerateInventory`+фильтр) **работает**, но это нативный
  black-box с нетривиальной семантикой обхода (`LEVELORDER` в `enumdump` давал `null`-записи
  для вложенного — тонкость обхода, не поломка API). B управляемее и понятнее → выбран B.
- **Карго vs слот**: структурно (B) без чтения локации; руки `EnumerateInventory` ВОЗВРАЩАЕТ
  (`raw=Mosin9130 loc=HANDS`) — поправка к ресёрчу (п.7.2).
- **AmmoBox_*_20Rnd** (`Box_Base`) → `GetCategory==OTHER` (пробел); калибр из конфига
  `Resources`. → часть №2.

**Новые дефекты (вскрыты spike, отдельные пункты):**
- **Аммо-пачка не ложится в карго при выдаче loadout'ом**: `Ammunition_Base` через
  `CreateInInventory` (путь `dmLoadoutApplier`) не виден ни `invdump`, ни `GetCargo()`
  (в сц.1/3/4 «исчез»). Проверить: это `dmLoadoutApplier` или само создание пачки.
- **`dmLoadoutApplier.FillAttachments` игнорирует `SlotName`**: GPS лёг в КАРГО рюкзака, а не
  в слот `WalkieTalkie`.
- **Loadout-созданные предметы получают health 0** (`CreateInInventory` на надетой одежде
  без `Health`-поля) → `dmRequirements.Update` фильтрует как `ruined` (`GetHealth01()<=0`) →
  не ранжируются/не видны в `reqdump`. Обход в тестах — явный `Health={Min:1,Max:1}` в loadout.
- **Loadout не кладёт предмет в карго ЖИЛЕТА (слот Vest)**: `Loadout + Apple -> SmershVest`
  логирует успех, но `invdump cargo=none`; при этом слот `Body` (куртка) заселяется. Т.е.
  `CreateInInventory` на надетом жилете молча теряет предмет. Отдельно от «health 0».
- **`Ammo_762x54` классифицируется как MAGAZINE** (`GetCategory` проверяет `IsMagazine()`
  раньше `IsAmmoPile()`; `Magazine` typedef покрывает и пачку) → дедуп с магазинами. Проверить
  семантику `IsMagazine()` vs `IsAmmoPile()` перед Атомом 4 (калибровый ранг).

## Обсуждение №1 (eat/drink → состояние)

Персональные рефлексы (есть/пить/лечиться) не должны висеть IDLE-интентом. Триггеры:
«хочу есть», «хочу пить», «есть ранения/переломы/болезни». Механизм параллельного
встраивания важных/неважных персональных интентов. Вопрос: eat/drink уже обсуждался как
перемещение в состояние заботы о здоровье? По факту — НЕТ: `dmBotIntent_EatDrink` до сих
пор persistent IDLE-интент (Spawn), а `dmBotState_MedicalCare` покрывает только медицину.
`requirements.md:37` «Потребность → цель» — `[ ]` (не реализовано, «следующая фаза»).
