# Proposal: лут и исследование (эстетика + механика, 3 слоя)

> Уточняет сырые заметки `docs/looting-and-exploration.md`. Статус: proposal — код не писан.

## Цель и движущие силы

Бот должен выглядеть как игрок и вести себя как игрок. Две независимые движущие силы:

- **эстетика** — неотличимость от игрока: бот ходит, исследует здания, осматривается
  (`Explorer` + `LookAround`);
- **механика** — реальный лут: взять нужное, выбросить лишнее
  (`Wishlist`/`Requirements`/`PickUp`).

Главный архитектурный принцип: **связи между доменными классами выносятся на слой выше**.
Домены — чистые (хранят состояние, отвечают на вопросы, никого не пишут); «намерения»
(координатор нужд + интенты) их связывают.

## Слой 1 — доменные провайдеры (чистые, без перекрёстных записей)

1. **Classification** — `GetCategory(ItemBase) → enum` на ванильном наследовании
   (`IsInherited(Edible_Base)`, `IsWeapon()`, `IsMagazine()`, `IsClothing()`,
   `IsInherited(WeaponCleaningKit)` и т.д.).

2. **Wishlist** — реестр желаний + скорер:
   - `SetDesired(itemClass, necessity)` / `RemoveDesired`;
   - `SetJunk(itemClass)` / `RemoveJunk`;
   - `Ignore(item)` / `Unignore(item)` (с таймаутом авто-Unignore);
   - `CalcDesired(item) → 0..1` — сам скорер: junk→0, ignore→0, desired→значение, иначе
     fallback (калибр под моё оружие, одежда лучше надетой, есть ли оружие и т.п.).

3. **Requirements** — состояние инвентаря (только описывает, никого не пишет):
   - `Update()` (тик 5с): индекс необходимости каждого предмета (первая еда=1, вторая=0.5…;
     патроны под мой калибр всегда 1);
   - `GetDiscardOrder() → array<EntityAI>` (сортировка «выбросить в первую очередь»);
   - `GetRepairPairs()`, `GetRuined()`, `IsFull()`.

4. **Explorer** — состояние мира (эстетика):
   - `OnUpdate()` (раз в минуту): здания в 50 м, флаг «посещено», привязка предметов к
     зданию (у предмета флаг «проверено»);
   - `GetNearest(radius) → непосещённое здание`; периоды забывания (500 м / 200 м).

## Слой 2 — оценка нужд (`dmNeeds`, отдельный класс внутри бота)

`dmNeeds` — атрибут бота (как `dmAiming` у пешки), тикается из `Update` бота, когда нужно
(раз в ~5с). Единственное место, где **инвентарь превращается в желания**:

- нет оружия → `Wishlist.SetDesired(Weapon_Base, 1)`;
- есть повреждённое и нет ремкомплекта → `SetDesired(ремонт, 1)`;
- нет ножа → `SetDesired(нож)`;
- `Requirements.IsFull()` → выставить флаг «нужна эвакуация» (drop).

Так `Requirements` остаётся чистым анализатором, а связь «инвентарь → желания» живёт здесь.

## Слой 3 — интенты + состояния (поведение, эстетика)

- `PickUp` (EXCLUSIVE): путь к предмету → поднять (гейт: нет места/недостижимо).
- `LookAround` (EXCLUSIVE): зайти в здание, пройти комнаты — **ради правдоподобия**.
- `Drop`/`Evacuate`: выбросить по `GetDiscardOrder()` при переполнении.
- **`Exploration`** (состояние) — дефолт-поведение: блуждание к непосещённым зданиям
  (`Explorer.GetNearest`) + осмотр (`LookAround`) + оппортунистический подбор
  (`PickUp` при `CalcDesired > порог`).

## Ответ: «блуждание вне лута» — да, это дефолт

Блуждание к непосещённым зданиям — это **дефолт-поведение** (эстетика), независимое от
лута. Бот просто ходит и осматривается, как игрок; подбор — оппортунистический, внутри
`Exploration`, по факту «вижу нужное — беру». Т.е. `Exploration` и есть roadmap-задача
`Looting` (T16), расширенная эстетикой; отдельного состояния «Looting» не нужно — подбор
это под-интент внутри `Exploration`.

## Гибкость / поддерживаемость

- Домены чистые — тестируются и меняются изолированно.
- Одна точка связи «Requirements → Wishlist» — в `dmNeeds`; одна точка «Explorer → путь» —
  в `Exploration`.
- Новые нужды — модификатор в `dmNeeds`, не трогая домен и поведение.

## Фазы

1. Classification (`dmLoot.GetCategory`).
2. Wishlist (`CalcDesired`) + Requirements (инвентарь/индексы).
3. `dmNeeds` (слой 2, перевод инвентаря в желания).
4. PickUp + Drop + Exploration (эстетика + оппортунистический лут).
