# Рефакторинг целей: ООП-иерархия `dmTarget` (эпик)

Статус: **не начато** (спека согласована, ждёт А0). Ветка: `feature/noise-attention`.
Референсы заказчика — `docs/plans/target-refactor-references.md` (если решение сомнительно —
смотри референсы; если всё равно непонятно — вопрос заказчику через оркестратора).

## 1. Цель и мотивация

Сейчас `dmTarget` — один класс, который несёт и «предсказание» (сущность рядом, но не
определена — регистрируется зрением для оптимизации), и «определённую» цель, и логику
внимания. Он раздут. Нужно разделить типы целей по объектной модели и дать мгновенные
реакции через атомарные триггеры на изменение списка целей.

## 2. Эволюционная лестница цели

Цель эволюционирует строго вверх, шаг за шагом:

```
Dummy (фантом) ──звук──▶ Sound ──опознан──▶ Identification
Dummy (фантом) ──виден──▶ Identification
```

- **Dummy (фантом)** — бот не знает о сущности ничего. Запись нужна только чтобы в конце
  концов стать настоящей целью. Источник: зрение-оптимизация (сущность в боксе, ещё без LOS).
- **Sound** — бот слышит звук, но не знает, что его производит. Необязательный шаг.
- **Identification (опознание)** — бот знает, что это: `Player` / `Zombie` / `Animal` / `Entity`.

Переход происходит, когда что-то **раскрывает секрет** цели: звук или прямая видимость.
Механизм перехода — `ReplaceTarget` (см. §5): удалить старую запись, добавить новую
(в Enfusion нельзя менять класс существующего объекта).

## 3. Иерархия классов

Папка: `src/core/4_World/Entities/Bot/Target/`. `dmTarget` становится абстрактным.

```
dmTarget (abstract)                              — общая память: m_Entity, m_LastPosition,
                                                  m_LastPositionSpread, m_LastDistance,
                                                  m_HasLOS, m_EverSeen, m_LastContact,
                                                  m_LastDamage, m_NextLOSUpdate, m_Threat,
                                                  m_Friendly + базовые методы (IsVisible,
                                                  LastPosition, GetLivePosition, …)
├── dmTargetDummy                               фантом (тип не определён)
├── dmTargetSound (abstract)                    звук (держит m_Attraction + m_AttentionCooldownUntil)
│   ├── dmTargetShooting                        звук стрельбы
│   ├── dmTargetFootsteps                       звук шагов
│   ├── dmTargetExplosion                       звук взрыва
│   ├── dmTargetDrop                            звук «что-то бросили рядом»
│   ├── dmTargetDroppedBullet                   «пуля упала рядом» (см. §7 — позиция нетривиальна)
│   └── dmTargetNoise                           прочий/неизвестный звук
├── dmTargetPlayer                              игрок или бот (разницы не делаем)
├── dmTargetZombie                              зомби
├── dmTargetAnimal                              животное
└── dmTargetEntity                              неживое (машина, костёр, предмет…)
```

Замечание по названиям: `dmTargetDrop` (звук «бросили») ≠ `dmTargetEntity` (опознанное
неживое). `dmTargetDroppedBullet` — отдельный случай попадания пули.

## 4. Классификаторы и геттеры (на `dmTarget`, паттерн Expansion)

Полный набор существ DayZ (больше типов нет): `PlayerBase` (человек + ИИ-бот) +
`ZombieBase` (заражённые) + `AnimalBase` (животные) + всё остальное `EntityAI` (неживое).

Методы на базовом `dmTarget` (в базе возвращают `false`/`null`, переопределяются в подклассах):

- `bool IsPlayer()` — игрок ИЛИ бот (`PlayerBase`).
- `bool IsPlayerAI()` — именно ИИ-бот (`dmAISurvivorBase`). `IsPlayer` ⊇ `IsPlayerAI`.
- `bool IsZombie()` — зомби (`ZombieBase`).
- `bool IsAnimal()` — животное (`AnimalBase`).
- `bool IsEntity()` — неживое (`EntityAI`, не `Man`/не `DayZCreature`).

Типобезопасные геттеры (в базе `null`, переопределяются в подклассах):

- `PlayerBase GetPlayer()` — только для Player (иначе null).
- `ZombieBase GetZombie()` — только для Zombie.
- `AnimalBase GetAnimal()` — только для Animal.
- `EntityAI GetEntity()` — общий доступ к сущности (вместо прямого `m_Entity`).

Паттерн потребления (эталон Expansion):
```
if ( target.IsPlayer() )
{
    PlayerBase player = target.GetPlayer();
    ...
}
```

**Инкапсуляция**: никаких прямых доступов к полям `dmTarget` извне — вся механика скрыта
внутри Target. Есть техдолг по прямым доступам (напр. `t.m_Entity`, `t.m_LastPosition`,
`t.m_Threat`) — прибираем постепенно в ходе рефакторинга.

## 5. Триггеры (атомарные методы скоупа целей)

Живут на мозге `dmAISurvivor`; управляют **`dmTargetManager`** (новый класс, куда переносятся
сложные механики: сам массив целей, поиск по EntityAI, дедуп и т.д.).

- `AddTarget(dmTarget)` — добавить новую цель (с гарантией дедупа по EntityAI).
- `DelTarget(dmTarget | EntityAI)` — удалить цель.
- `ReplaceTarget(EntityAI, dmTarget)` — найти существующую цель по EntityAI → удалить → добавить новую.

**Инвариант**: на одну `EntityAI` — не более одной цели; не бывает двух классификаций одной
сущности. Это гарантирует прямой переход по лестнице (фантом → звук → опознание).

На `AddTarget` **опознанной** цели впоследствии вешаем мгновенную реакцию: оценка опасности →
переход FSM (инструмент для боя/реакций).

Весь остальной код работает с целями **только через методы** (базовый класс), поэтому приведение
классов нужно лишь там, где надо понять, что это за класс и работать с ним соответственно.

## 6. Инвариант «одна цель на одну EntityAI»

Все цели привязаны к `EntityAI`. `dmTargetManager` гарантирует: перед `AddTarget` ищет по
сущности, при наличии — не дублирует (либо `ReplaceTarget`). Это важно для прямого перехода
по лестнице целей.

## 7. Специфика `dmTargetDroppedBullet` (нетривиально)

> **УТОЧНЕНО (эпик шумов).** Пункт о «серединной позиции» и «не перетирать звук выстрела» —
> **отменён** как переусложнение. Заказчик уточнил семантику `m_LastPosition` («последняя точка,
> где бот думает, что цель есть»): обновляется любым контактом, шум → позиция шума. Спец-обработка
> BULLETIMPACT (midpoint/return-early) НЕ делается. См. `docs/decisions.md` (запись
> `noise: lastKnownPosition`). Единственная содержательная часть шума падения пули — **ссылка на
> стрелка** (`source`), а не пересчёт позиции.

Попадание пули — позиционный шум, но мы умеем определять стрелка (через мост `source → GetHierarchyRootPlayer`).
- `dmTargetDroppedBullet.m_Entity` = **стрелок** (игрок, совершивший выстрел) — это вся суть;
  позиция цели обновляется штатным потоком `HearNoise` (позиция шума = позиция падения пули).

## 8. Удаление `m_Attractiveness` (мёртвый код)

Полностью вырезать: поле `m_Attractiveness`; параметр `attractiveness` в `DiscoverTarget`/
`HearNoise`; гейт `t.m_Attractiveness > DM_HUNT_MIN_ATTRACTIVENESS` в `GetHuntTarget`
(Hunting остаётся входить только по `threat >= 0.5`); константы `DM_TARGET_ATTRACT_*` /
`DM_NOISE_ATTRACTIVENESS_*` / `DM_HUNT_MIN_ATTRACTIVENESS`; строку `attract=` в дампе
`/bot vision`; упоминания в документации.

Примечание: Hunting после этого может быть нерабочим — допустимо до конца эпика, починим.

## 9. Атомы (декомпозиция)

- **А0** — классификаторы `IsPlayer/IsPlayerAI/IsZombie/IsAnimal/IsEntity` (централизация).
- **А1** — скелет: перенос `dmTarget.c` → `Bot/Target/`, `dmTarget` абстрактный, файлы
  подклассов; все `new dmTarget()` → `dmTargetDummy` (поведение не меняется). Build+load регрессия.
- **А2** — `dmTargetManager` + триггеры `AddTarget/DelTarget/ReplaceTarget` + дедуп по EntityAI;
  все вставки/удаления через них.
- **А3** — эволюционная лестница: зрение → `Dummy`, LOS → `ReplaceTarget(Dummy→Player/Zombie/
  Animal/Entity)`, слух → `ReplaceTarget(Dummy→Sound)`, опознание звука → `ReplaceTarget(Sound→Identification)`.
- **А4** — удаление `m_Attractiveness` (+Hunting) — **без E2E** (по указанию заказчика).
  ✅ **Выполнено** (grep по `src/` чист): поле удалено, сигнатуры `DiscoverTarget`/
  `HearNoise` без `attractiveness`, Hunting входит только по `threat >= 0.5`.
- **А5** — ADM-лог «новая цель» (`[bot:heard]`) + внимание поверх иерархии (закрывает разрыв
  «`[bot:heard]` не пишется»).
- **Финальный E2E** — серьёзная регрессия всех механик (ничего не сломано).

## 10. Рабочие правила (обязательные)

- **Перед каждым атомом — обсуждение** деталей с заказчиком через оркестратора.
- **Ключевые решения — только с согласия заказчика.** Без самостоятельных ключевых решений.
- **На ключевых точках — показываем работу «Придире»** (`dayz-reviewer`).
- **Коммит — только после E2E** (`PASS`). Нефункциональные изменения (добавление неиспользуемых
  методов, доки) — достаточно **дымового теста** (сервер и клиент запускаются, без краша).
- **Референсы заказчика** — источник истины при сомнениях; если непонятно — вопрос через оркестратора.
- Работать аккуратно: рефакторинг не должен сломать существующие механики.
