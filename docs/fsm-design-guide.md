# Гайд проектирования FSM-состояний ботов

Правила, которым нужно следовать при создании состояний/интентов FSM ботов. Выведены
из реальных ошибок при разработке сопровождения (Follow) — см. «Анализ ошибок» ниже.
Загружать вместе со скиллом `dayz-ai-bot`; при ревью сверяться с этим списком.

## Главный принцип

**Логика состояния должна быть максимально простой.** Никакой предиктивной логики —
экстраполяция, планирование, сложные эвристики, «умные» рампы. Простые правила и
плоская геометрия. Если решение не укладывается в 2–3 простых шага — оно слишком
сложное для бота.

## Тезисы HOWTO

1. **Простота > точность.** Предиктивная экстраполяция скорости/позиции была выброшена
   в пользу простого якоря `pos + vel·1.5 + перпендикуляр·сдвиг`. Бот не должен
   «симулировать» — он должен следовать простому правилу.

2. **Якорь по вектору движения, а не по ориентации цели.** Для движущейся цели сторона
   считается от `Velocity` (реальное направление движения), а не от `GetDirection()`
   (куда смотрит). Игрок бежит вперёд, а смотрит вбок — «плечо» по facing было ошибкой.

3. **Разделяй «догнать» и «держать строй».** Это разные режимы: догон — `MoveTo`
   (pathfinding к последней известной позиции), строй — отдельный непрерывный интент
   (`FollowTo`) с динамическим якорем. Не мешай их в одном интенте.

4. **Скорость — просто.** Дистанция до точки + правило «не медленнее цели»
   (`max(dist-скорость, скорость цели)`). Без дедлайнов/рамп/экстраполяции — они дают
   осцилляцию sprint↔jog.

5. **Рандом (бок/сдвиг) — один раз на вход**, запоминать и не перебрасывать. Иначе бот
   «плавает» вокруг цели.

6. **Переходы декларативны.** `weight > 1.0` — приоритетный (детерминированный) переход;
   `Require`/`BlockWhen` — условия ребра; `CanEnter()` — «есть ли у меня данные» (напр.
   цель воспринята). Состояние НЕ диктует, куда идти — только `EXIT` («работа кончилась»).

7. **Фильтруй мёртвые цели в запросах** (`GetHostileTarget`/память). Труп в списке целей
   → осцилляция `Fight↔Idle` (угроза → бой → цель мертва → выход → угроза → …).

8. **Перцепция-гейт + «магия» восстановления.** Следуй только за воспринятой целью;
   при потере видимости — простой фолбэк (через N секунд «узнать» позицию), а не сложная
   логика поиска.

9. **Тестируй слой изолированно.** Интент → состояние → пресет. Для каждого слоя —
   отладочная команда (`/bot melee`, `/bot give`), чтобы проверить механику до подключения
   к FSM.

10. **Cooldown повторного входа.** Если состояние вышло по «не могу работать» (нечем
    стрелять / нет цели), оно ставит `m_CooldownGameTime` (время истечения) — `CanEnter()`
    возвращает false, пока cooldown не истёк. Так гасится осцилляция `Shooting↔Idle`: бот
    не перезаходит в состояние, которое только что покинул по той же причине. Подробности
    в `docs/combat.md` (§ Cooldown повторного входа).

## Анализ ошибок: Follow, итерация 1 → сейчас

**Итерация 1 (до переделки):** один `MoveTo` к якорю; якорь — «плечо» по `GetDirection()`;
скорость — `SetPreferredSpeed` по дистанции (sprint>15/jog>10/walk); выход по «цель стоит +
бот в месте».

**Что было не так (по порядку находок):**

- **Inline-вычитание векторов** (`a.GetPosition() - b.GetPosition()` давало 0) — готча
  Enfusion, не про логику, но стоила двух дней отладки. → правило: позиции в локалы,
  потом арифметика (в `codeguide.md`).
- **«Плечо» по facing** неверно для бегущего игрока (смотрит вбок). → якорь по `Velocity`.
- **Скорость через дедлайн** (`CalcSpeed` + `m_ReachDeadline`) давала осцилляцию
  sprint↔jog из-за устаревшей цели. → заменили на `SetPreferredSpeed` по дистанции, затем
  на простую `distToAnchor` + «не медленнее цели».
- **`Follow EXIT` на любую угрозу** — бот бросал сопровождение. → «оборона» (4 м) для
  Follow vs «агрессия» (15 м) для Idle.
- **Осцилляция `Fight↔Idle`** — труп оставался в `m_Targets`. → фильтр `IsAlive()` в
  запросах.
- **Сложная экстраполяция** (скорость по зазору через 1 с + path-экстраполяция +2 с +
  velocity-match) — переусложнение. → выброшено, остался простой якорь.

**Главный вывод (личный):** категорически нельзя использовать сложную логику —
логика должна быть максимально простой. Любая «умная» надстройка (экстраполяция,
планирование) ломается и усложняет отладку; простой геометрический якорь работает
надёжнее и предсказуемее.
