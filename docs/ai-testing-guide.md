# Руководство ИИ-агента: E2E-тестирование botorama перед фиксацией

Назначение — операционный ранбук **для ИИ-агента** (оркестратора). Перед коммитом
результата работы агент обязан пройти полный цикл: собрать мод → задеплоить →
запустить сервер → прогнать проверку → сверить логи → и только потом фиксировать.

В отличие от `docs/tester-guide.md` (чат-команды для человека-тестировщика), здесь
описано, как агент **сам** выполняет цикл на Linux-хосте, без Steam-GUI и без игрока.

## 1. Сборка мода

Мод собран из 7 PBO (`cons`, `reg`, `core`, `map`, `loadout`, `roads`, `test`) в `src/`.
Сборка идёт Windows-тулзами DayZ Tools под Proton — headless, без открытия Steam-GUI.

### 1.1 Тулчейн

Всё лежит в Steam-библиотеках:

| Что | Путь |
|---|---|
| DayZ Tools | `/mnt/deep-space/Steam/steamapps/common/DayZ Tools` (appid `830640`) |
| AddonBuilder | `…/DayZ Tools/Bin/AddonBuilder/AddonBuilder.exe` |
| CfgConvert | `…/DayZ Tools/Bin/CfgConvert/CfgConvert.exe` (вызывается AddonBuilder'ом) |
| DSSignFile | `…/DayZ Tools/Bin/DsUtils/DSSignFile.exe` (вызывается AddonBuilder'ом) |
| Proton | `/home/devalio/.local/share/Steam/steamapps/common/Proton Hotfix` |
| Рантайм | `/home/devalio/.local/share/Steam/steamapps/common/SteamLinuxRuntime_4` |
| Wine-префикс | `/mnt/deep-space/Steam/steamapps/compatdata/830640/pfx` |
| Ключ подписи | `/home/devalio/dayz/Work/Keys/devalio.biprivatekey` (+ `devalio.bikey`) |

### 1.2 Цепочка запуска (восстановлена из живой Steam-сессии)

```
SteamLinuxRuntime_4/_v2-entry-point --verb=waitforexitandrun -- \
  'Proton Hotfix'/proton waitforexitandrun '<exe>' <args>
```

Окружение, которое поднимает Steam (полный набор — в `tools/build.sh`):

```
STEAM_COMPAT_DATA_PATH=/mnt/deep-space/Steam/steamapps/compatdata/830640
STEAM_COMPAT_CLIENT_INSTALL_PATH=/home/devalio/.local/share/Steam
STEAM_COMPAT_INSTALL_PATH="/mnt/deep-space/Steam/steamapps/common/DayZ Tools"
STEAM_COMPAT_LIBRARY_PATHS=/home/devalio/.local/share/Steam/steamapps:/mnt/deep-space/Steam/steamapps
STEAM_COMPAT_TOOL_PATHS=…/Proton Hotfix:…/SteamLinuxRuntime_4
SteamAppId=830640
```

### 1.3 CLI AddonBuilder

```
AddonBuilder.exe <source_dir> <dest_dir> [-prefix=<prefix>] [-clear]
                 [-include=<файл>] [-sign=<biprivatekey>]
```

- `<dest_dir>` — **каталог**, имя `.pbo` берётся из имени папки-исходника
  (для `src/cons` → `build/cons.pbo`). НЕ передавать имя файла.
- `-include` — include-список расширений (обязателен, см. ниже).
- `-sign` — ключ подписи (`.biprivatekey`); AddonBuilder сам вызывает DSSignFile.

### 1.4 Include-список

Файл `tools/include.lst` (semicolon-разделитель, с пробелами):

```
*.emat; *.edds; *.ptc; *.c; *.imageset; *.layout; *.ogg; *.agr; *.csv
```

**Обязателен**: без него полный билд (не `-packonly`) выкидывает `.c`-скрипты,
и остаётся только `config.bin`.

### 1.5 Запуск сборки

```
bash tools/build.sh
```

Собирает 7 модулей → `build/<модуль>.pbo` + `build/<модуль>.pbo.devalio.bisign`.

**Инкрементальная сборка** — когда `dayz-dev` изменил не все модули, собираем только
их (в отчёте dev указывает список изменённых модулей):

```
bash tools/build.sh --test --modules core,test
```

`--modules` берёт список модулей через запятую; остальные PBO в `build/` переиспользуются
как есть (`build.sh` НЕ чистит каталог при частичной сборке, а `-clear` AddonBuilder'а
prefix-scoped — чистит только свой модуль). Признак полной сборки — отсутствие `--modules`
(тогда `build/` чистится целиком). Дефолт `--modules` = все 7.

Перед сборкой `build.sh` очищает Temp wine-префикса
(`compatdata/830640/pfx/drive_c/users/steamuser/AppData/Local/Temp`) — AddonBuilder
чистит его сам, но медленно; ручная очистка ускоряет компиляцию и надёжнее.

### 1.6 Готчи сборки

- **Рантайм — только `SteamLinuxRuntime_4`.** `SteamLinuxRuntime_sniper`/`soldier`
  дают glibc 2.36, а Proton 11 требует ≥2.38 → `could not load ntdll.so:
  GLIBC_2.38 not found`. Правильная цепочка снимает проблему.
- **`-packonly` НЕ подходит** — он не делает `config.cpp`→`config.bin`.
  Нужен полный билд (binarize) + `-include` (иначе `.c` пропадают).
- **Include-файл — semicolon-разделитель**, не «одно расширение на строку»
  (переводы строк ломают разбор — билд молча ничего не производит).
- **Wineserver префикса один на процесс.** Пока в Steam открыт DayZ Tools
  (AddonBuilder/лаунчер), второй headless-запуск зависает на `wineserver -w`.
  Перед сборкой закрыть DayZ Tools (или убить его процессы — разрешено).
- Дополнительно проверить: `strings -a <pbo> | grep config.bin` — в каждом PBO
  должен быть `config.bin`, а в `core.pbo` — ещё `.agr` и `.ogg`.

## 3. Запуск сервера

Скрипт пользователя: `~/dayz-nasdara.sh` (запускается из-под `nohup`, т.к. работает
в foreground):

```
nohup ~/dayz-nasdara.sh > /tmp/dayz_console.log 2>&1 &
```

> **Готча (запуск из ИИ-агента)**: `nohup ~/dayz-nasdara.sh > /tmp/dayz_console.log 2>&1 &`
> **зависает** на таймауте bash-инструмента: `~/dayz-nasdara.sh` держит `./DayZServer` в
> foreground, а дочерний процесс остаётся привязанным к stdout/stderr pipe — инструмент
> ждёт завершения сервера. Правильная форма:
>
> ```
> setsid nohup ~/dayz-nasdara.sh >/tmp/dayz_console.log 2>&1 </dev/null & disown
> ```
>
> `setsid` + `</dev/null` + `disown` полностью отвязывают процесс от терминала/pipe.

Под капотом (скрипт чистит старые логи и стартует):

```
cd /mnt/deep-space/Steam/steamapps/common/DayZServer/
rm -rf ./profiles-nasdara/*.log *.ADM *.RPT *.mdmp
./DayZServer -cpuCount="6" -config=./nasdaraDZ.cfg -profiles=./profiles-nasdara \
  -mod=@Botorama; -doLogs -adminlog -port=2302
```

- Конфиг: `nasdaraDZ.cfg` (миссия `nasdara`, карта Чернорусь), профиль `profiles-nasdara`.
- **Моды: ТОЛЬКО `@Botorama`.** Никаких посторонних модов (без `@CF`, `@COT` и прочего) —
  ни на сервере, ни на клиенте. Если тест требует COT-команды — это отдельное согласование.
- **POI/здания (факты для тестов)**: (1) сервер пре-стримит ~5.5 тыс. статических
  зданий на старте — `buildingdump.registered` НЕ стартует с 0; проверяй привязку через
  `locId` ↔ `poidump.at` + `locCount > 0`, а рост — как тренд. (2) Id локации = порядок в
  `world_poi.json` (Черногорск=0, Новодмитровск=1); не зашивай Id по имени — сверяй
  `poidump.at` в рантайме.
- Рестарт: `kill <pid>` → `~/dayz-nasdara.sh` (сервер перечитывает новые PBO только
  при рестарте — hot-reload отсутствует).
- **Остановка (обязательно после прогона)**: `kill -9 <PID>` — PID бери через
  `pgrep -f '[.]/DayZServer '` (символьный класс `[.]`, НЕ `\.` и НЕ `DayZServer`), либо
  сверься по `ps aux`. Сервер не оставлять работающим после тестов. Если запускал
  клиент-наблюдателя — `pkill -f 'DayZ_x64.*e2e-observer'`.
  **Готчи**: (1) `pkill -f DayZServer` **и даже** `pkill -f '\./DayZServer '` (экранированная
  точка) само-матчатся, когда команда идёт через `bash -c`: в командной строке шелла
  остаётся литерал `DayZServer` (и `.` из `./DayZServer `) → regex матчит сам себя → `-9`
  убивает оболочку («зависание» на таймауте). Надёжно только символьный класс `[.]`: в
  argv остаётся `[.]`, а regex `[.]` матчит `.` (не `[.]`). (2) `pkill/pgrep -x DayZServer`
  НЕ матчит процесс, чей argv = `./DayZServer` (точное имя не совпадает с путём) — поэтому
  верификацию делай через `pgrep -f '[.]/DayZServer '` или сверкой по `ps aux`, а не по `-x`.

- **Процессы пользователя НЕ трогать (жёстко).** У девальо могут быть СВОИ запущенные
  DayZ-процессы (сервер/клиент). НЕ `kill`/`pkill` чужие `DayZServer`/`DayZ_x64`/`DayZ_BE`/
  `DayZLauncher`. Свой сервер поднимай на **своём порту** (не `2302` — его может занимать
  пользователь; бери свободный, напр. `2312`), профиль/конфиг — свой. Останавливай ТОЛЬКО тот
  процесс, который запустил сам (PID зафиксируй при `setsid nohup`, либо `pgrep` по своему
  порту/профилю). Чужой клиент (не `e2e-observer`) — не трогать. Если порт/профиль конфликтует —
  отчёт `BLOCKED` оркестратору, а НЕ убей чужое.

## 4. Чтение логов

RPT-лог сервера — `DayZServer/profiles-nasdara/DayZServer_<дата>.RPT` (последний —
по `ls -t`). Ключевые маркеры:

| Что ищем | Пример | Значение |
|---|---|---|
| Загрузка PBO | `Adding package '…@Botorama/Addons/<модуль>.pbo'` | все 7 PBO загрузились |
| Defines | `…dmBotorama_Cons,dmBotorama_Reg,dmBotorama_Core…` | цепочка `requiredAddons` встала |
| Версия мода | `[dmBot] Botorama initialized: 3.160` | `dmBotLog.LogVersion` (совпадает с `DM_BOTORAMA_VERSION`) |
| Ошибки скриптов | `SCRIPT (E)` / `[dmBot][error]` | реальные проблемы (не `(W)` warning'и) |
| Краш | `crash_*.log`, `error.log`, `*.mdmp` | смотреть stack |

Известные не-проблемы (были и до рефакторинга, игнорировать):
- `ANIMATION (E): Can't load @Botorama/Anims/cfg/skeletons.anim.xml` — фолбэк на
  ванильный скелет `DZ/Anims/cfg/skeletons.anim.xml`, боты работают.
- `[POIRegistry] read error …/world_poi.json` — нет данных карты в `$profile`
  (к `data/map/`, не к модулям).
- `No entry 'bin\config.bin/CfgVehicles/enfAnimSys.*'` — штатные config-варнинги
  наследования; `STR_DN_* not found` — ванильные локализационные варнинги.

## 5. Автотесты (файловый мост)

Автотесты управляются **файловым мостом** — без игрока и без HTTP-сервиса. Агент
кладёт JSON-сценарий, мод исполняет его на сервере, агент читает JSON-результат и
tail'ит RPT. Протокол, словарь команд и схема результата — `docs/plans/e2e-automation.md`;
каталог регрессионных сценариев — `tools/e2e/`.

Цикл (см. §5.1–5.3): собрать → задеплоить → старт → сценарий → результат → фиксация.

### 5.1 Выбор defines при сборке

`tools/build.sh` принимает флаг, задающий набор `defines[]` (debug-домены логирования):

| Режим | Флаг | defines[] |
|---|---|---|
| **Прод** | `--prod` | только `DM_BOT_PROFILE` |
| **Функциональный** (дефолт) | *(без флага)* | как закоммитил `dayz-dev` (релевантные домены фичи) |
| **Регрессионный** | `--test` | все event-домены из `tools/defines_test.txt` |

Регрессию тестировщик гоняет с `--test` (полное покрытие event-доменов); per-frame
домены (`DM_BOT_TRACE_LOOK`, `DM_BOT_DEBUG_PERFRAME_MOVING_LOG`) в `--test` НЕ входят
(спам) — их включает `dayz-dev` точечно, если конкретный сценарий их проверяет.

### 5.2 Запуск сценария

```bash
# маркер уже лежит (см. e2e-automation.md)
cat > "$PROFILE/dmBotorama/e2e/in/<job>.json" <<'EOF'   # атомарно: .tmp → rename
{ "Name": "<job>", "Timeout": 60, "Steps": [ ... ] }
EOF
# дождаться out/<job>.result.json; при провале — tail RPT
```

Результат: `out/<job>.result.json` (`Status`: `ok`/`error`/`timeout`, `Steps[].Ok`,
`Snapshot[]`). `bool` в JSON = `1`/`0`.

### 5.3 RPT-канал моста

Жизненный цикл моста пишется в RPT под доменом `DM_BOT_DEBUG_E2E` (входит в `--test`):
`enabled`, `job X picked up`, `step N: op=…`, `job X → status=…`, ошибки.

### 5.4 Ранний стоп на аномалии (не ждать таймаута)

Если сценарий явно «умер» (деградировал в зацикленное поведение), НЕ ждать
`wait`-таймаут — стопить сразу и собирать улики. Признаки для вождения (`[CAR]`
лог, домен `DM_BOT_DEBUG_CAR`):
- **Осцилляция/дёрганье на месте**: `angle` флапает `±3.0–3.13 рад` (±178°),
  `reverse` переключается каждые ~2 с, `dist` до цели РАСТЁТ (машина откатывается),
  `steer` замирает на `±0.9–0.99` (полный занос). Это ключевой сигнатурный паттерн
  «цель за кормой → знак руля нестабилен».
- **Проскок дуги**: `m_DriveRouteIdx` прыгает сразу через несколько точек
  (`dot < -0.2` скипает подряд) — маршрут слишком тесный для текущей скорости.

Действия при обнаружении: `clearall` + `clearobj` (уборка), зафиксировать в отчёте
окно `[CAR]`-лога (speed/angle/reverse/steer/dist/gear) за ~30–60 с до/после
триггера, координаты точки срыва и гипотезу причины. Таймаут — только фолбэк.

## 5.5 Дисциплина функциональных тестов (обязательно)

Три жёстких правила — чтобы прогоны были быстрыми, тихими и однозначными.

### 5.5.1 Таймауты: поллинг с ответом ≤15 с, НЕ длинный sleep

- **Запрещены** `sleep 600` / `sleep 460` и подобные «сплю N минут». Ожидание чего
  бы то ни было — только **поллингом с коротким периодом и ранним ответом**: `wait`-оп
  с `Timeout ≤ 15 с` и чётким критерием успеха/провала, либо цикл grep/проверки
  результата каждые ~2 с с общим таймаутом ≤ 120 с.
- Если за 15 с нет однозначного ответа «прошло/упало» — это не повод увеличивать
  sleep, а сигнал: критерий шага плохой. Переформулируй шаг так, чтобы он давал
  однозначный ответ (явная e2e-ручка, `wait` на `carpos`/`reached`/`Alive`/`Moving`).
- Долгое вождение (маршрут) — дроби на этапы: `driveto` → серия коротких `wait`/`cardump`
  по контрольным точкам, а не один `sleep` до конца.

### 5.5.2 DEBUG-домены: для функционального теста — только нужные

- **Функциональный тест** = `--prod` + `--define <нужный домен>` (напр. вождение —
  `--define DM_BOT_DEBUG_CAR`). НЕ `--test` (все event-домены сразу) — это регрессия.
- `--test` (полное покрытие из `tools/defines_test.txt`) — **только после ошибки**,
  чтобы повторить прогон с расширенными логами для диагностики. На функциональном
  прогоне все домены не включать.
- Per-frame домены (`DM_BOT_TRACE_LOOK`, `DM_BOT_DEBUG_PERFRAME_MOVING_LOG`,
  `DM_BOT_DEBUG_DRIVE_TELEMETRY`) — НИКОГДА на функциональном прогоне (спам каждый кадр);
  только точечно при диагностике конкретного механизма.

### 5.5.3 Лог-шум окружения: один settlement-бот, без спама MoveTo

- Перед прогоном убедиться, что в `$profile:dmBotorama/map/spawn.json` стоит
  `"MaxBots": 1` (функциональному тесту хватает ОДНОГО settlement-бота; дефолт 40 —
  для «продакшн-подобной» нагрузки, на функциональном прогоне он даёт лишний шум).
- Спам `MoveTo: нет пути к …` от settlement-ботов (зациклены на недостижимые точки) —
  шум, не связан с тестом; в отчёте НЕ цитировать его как аномалию. Если он мешает —
  отметить, но не смешивать с результатом прогона.

### 5.5.4 Idle-режим сервера (нет игроков И ботов) — per-frame ждать нельзя

- DayZ-сервер без подключённых игроков **и** без заспавненных ботов уходит в **Idle**
  и перестаёт обрабатывать фреймы (`OnUpdate`/тики не идут). Поэтому **per-frame**-ожидания
  (e2e-мост `dmE2EBridge.Tick`, спавн-менеджер ботов, реакция/движение бота) НЕ завершатся
  без живого игрока — поллинг зависнет.
- **Правило**: полагаться только на **init-time** маркеры RPT (пишутся при старте миссии,
  не зависят от Idle): `Botorama initialized: <ver>`, `SCRIPT (E)`, defines миссии, отсутствие
  `base class not found`, permission-артефакты. Per-frame/поведенческие проверки — только при
  подключённом наблюдателе; нет наблюдателя → `BLOCKED`, НЕ висеть.
- Каждый поллинг — с жёстким таймаутом ≤40 с и отменой по таймауту (поллинг раз в ~2 с);
  по таймауту — фиксировать `TIMEOUT`/`BLOCKED` с тем, что успел прочитать.

## 6. Клиент-наблюдатель (опционально, только по запросу)

Для визуального подтверждения человек на этом хосте может смотреть тест в реальном
времени: тестировщик запускает рабочий клиент DayZ, который автоподключается к
локальному серверу, а сценарий телепортирует/поворачивает игрока к сцене.

> **Правило**: наблюдатель нужен ТОЛЬКО когда (а) оркестратор/человек явно сказал
> «с наблюдателем», или (б) тест требует визуального подтверждения. По умолчанию
> e2e-тесты **headless** — без клиента.

> **`e2e-observer` — это ЧЕЛОВЕК-наблюдатель, а не скрипт.** Агент НЕ симулирует ввод
> с клавиатуры и НЕ эмулирует команды/наблюдение за человека. Команды в чат и действия
> наблюдения вводит **сам человек** (оркестратор/пользователь) на хосте. Задача агента —
> поднять сервер + клиент и собрать логи/пруфы (RPT, `result.json`, клиентские пробы),
> а НЕ печатать за человека. `Op observe` — это телепорт первого подключённого игрока к
> сцене через мост, а не «агент управляет наблюдателем».

- **Готча `nasdara`**: `nasdara` — ВСТРОЕННЫЕ файлы игры (карта/террейн), их НЕ подключать
  со стороны клиента в `-mod=`. Клиенту нужен ТОЛЬКО `@Botorama` (тот же `-mod=@Botorama`,
  что и на сервере). Ранее `tools/run-client.sh` ошибочно добавлял `nasdara` в `-mod=` →
  map mismatch; убрано.
- Запуск клиента: `bash tools/run-client.sh` (Proton, appid 221100, `-connect=127.0.0.1:2302`,
  `-name=e2e-observer`, `-mod=Z:\...\DayZServer\@Botorama`, `-window -noPause -nosplash -skipIntro`).
- **Ожидание входа наблюдателя — ПОЛЛИНГОМ ЛОГА, максимум 60 с.** Игрок заходит за ~20–30 с.
  Вместо `sleep` гоняй цикл: grep свежего RPT на `Player "e2e-observer"` (или `is connected`) раз в
  ~2 с, **таймаут 60 с (1 минута), не больше**. Вход в игру занимает максимум 1 минуту; если за это
  время нет строки входа — ЖДАТЬ БЕСПОЛЕЗНО, стоп и отчёт `BLOCKED` (клиент не стартовал/завис).
  Аналогично сервер: `Botorama initialized` — тот же короткий таймаут. **Никаких «20 попыток × 30 с =
  10 минут»** — это недопустимо. Если в логе `client=[]` / нет `is connected` — наблюдатель НЕ вошёл,
  повторно поллинг не поможет, разбирайся с причиной (порт/префикс/зависший клиент).
- **Несовместимость с живой сессией пользователя.** Наблюдатель (`run-client.sh`) и клиент пользователя
  делят один wine-префикс `221100`; запуск наблюдателя «перехватывает» и убивает сессию пользователя.
  Перед запуском наблюдателя — убедиться, что у пользователя НЕТ активной сессии DayZ в этом префиксе
  (иначе нужен отдельный префикс — клон 221100).
- Op `observe` (в сценарии): телепорт **первого** подключённого игрока
  (`Pos` + `Yaw`) — `SetPosition(SnapToGroundExactly)` + `SetOrientation(Vector(Yaw,0,0))`.
  Если игрок ещё не зашёл — `Reason="no player connected"`, повторить после подключения.
- Первый прогон — проверить эмпирически: нужен ли запущенный Steam, `DayZ_x64.exe`
  напрямую или `DayZ_BE.exe`, формат `-connect` (`:2302` vs `:2302:2303`).

### 6.1 Клиентские логи и маркер клиентского моста (важно — НЕ путать с сервером)

Каталоги клиента под Proton-префиксом compatdata 221100 (путь `…/pfx/drive_c/users/steamuser/`):

| Что | Путь |
|---|---|
| `$profile:` (FileIO: маркер/джобы клиентского моста) | `AppData/Local/DayZ/` (там же `script_*.log`/`.RPT`) |
| Сохранения/настройки персонажа (`DayZ.cfg`, `*.DayZProfile`, `chars.*`) | `Documents/DayZ/` (НЕ `$profile:`) |

- **`[dmBot]`/`[E2EC]`-логи клиента пишутся в `AppData/Local/DayZ/script_*.log`**, а НЕ в
  `.RPT`. Грепать `.RPT` на `[E2EC]` — ошибочно (вернёт 0). Клиентский мост тикает
  (`[E2EC] bridge tick active`), даже когда «клиент не вошёл в игру» — это НЕ признак сбоя.
- **Маркер клиентского моста** — `AppData/Local/DayZ/dmBotorama/e2e-client/enabled` (создать
  вручную). Джобы — `AppData/Local/DayZ/dmBotorama/e2e-client/in/<job>.json`; результат —
  `…/out/<job>.result.json`. Пока маркера нет, мост пишет `[E2EC] enabled missing` (это
  штатно, не ошибка).
- **«Дошёл ли клиент до игры»** — по строке `Player Simulation entity` в клиентском `.RPT`
  (НЕ по `[E2EC]` tick). Загрузка мира/шейдеров может быть долгой (первый прогон — до 10–15 мин,
  консоль показывает `Fossilize shadercache`); НЕ убивать клиент раньше ~15 мин.

### 6.2 Поддержание наблюдателя живым (обязательно)

Персонаж-наблюдатель (`e2e-observer`) **нельзя программно оживить после смерти** (у ИИ-агента
нет способа переспавнить/воскресить игрока). Поэтому во время прогона с наблюдателем
**регулярно (раз в ~30–60 с) пополняй статы наблюдателя** через серверный мост (op `healplayer`):
здоровье, шок, гидрацию (вода), энергию (еда). Иначе персонаж умрёт от голода/жажды/потери
крови посреди длинного теста и клиентскую проверку придётся начинать заново с новым персонажем.
