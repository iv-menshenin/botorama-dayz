# Research: ломающие изменения DayZ 1.29 → 1.30 для мода botorama

Цель: перечислить ванильные API-изменения 1.29→1.30, релевантные моде botorama,
сопоставить с call-sites и проверить неофициальный гайд `docs/update130.md`.

## Метод

Сравнение **напрямую** двух деревьев:
- baseline **1.29**: `/home/devalio/dayz/Work/DayZ-Script-Diff/scripts` (`version=125372`).
- target **1.30**: `/home/devalio/dayz/Work/DayZ-Script-Diff-130/scripts` (`version=127250`).
- готовый core-диф `1.29→1.30`: `/home/devalio/dayz/Work/130-core-diff.txt` (GUI/editor исключены).

Каждый символ, который вызывает/оверрайдит botorama, проверялся `grep` по 1.30-дереву
(наличие + сигнатура), а не по 1.29. Удалённые методы искались по `^-`-строкам диффа.

---

## 1. Итог: compile-time поломок у botorama НЕТ (подтверждено по 1.30)

Все символы, которые вызывает или оверрайдит botorama, **присутствуют в 1.30 с теми же
сигнатурами**. Прежний вывод («ни один call-site не ломается»), сделанный по obsolete-тегам,
**подтвердился** при прямой проверке 1.30-дерева. Но нашлись **семантические** изменения
(§2) и новые obsolete-теги (§3), которых через метки 1.29 не было видно.

## 5. Расхождения гайда `update130.md` (по факту, против 1.29 и 1.30)

Гайд по-прежнему **ненадёжен**: большинство его «1.30-изменений» описывает рефакторинг,
уже случившийся в 1.29, либо несуществующие имена.

| § | Утверждение | Вердикт (проверено против 1.30) |
|---|---|---|
| §4.1 | `*TakeEntityAsAttachment` → `*TakeEntityToTargetAttachment` | неверно: реальные obsolete-имена `LocalTakeEntityTo*` → `LocalTakeEntityToTarget*` (EntityAI); `TakeEntityAsTargetAttachment` есть уже в 1.29 |
| §4.2 | `GetHeatIsolationInit` → `GetHeatIsolation` | неточно: ОБА живы в 1.30; изменилась только реализация (`m_HeatIsolation` → `ItemBaseType`) |
| §4.2 | `BuildPartServerEx`/`NeedElectricitySourceDevice`/`UpdatePathgraphEntityState`/`VehicleLightsComponent` | `VehicleLightsComponent` ДЕЙСТВИТЕЛЬНО появился в 1.30 (`vehiclelightscomponent.c`); остальные — нет (не существуют) |
| §4.2 | `IsScriptedLightsOn` → `LightIsOn` | `IsScriptedLightsOn()` жив и в 1.29, и в 1.30 (обёртка над `LightIsOn`) |
| §5 | `CarFluid` — новинка 1.30 | частично: в 1.29 уже был; в 1.30 стал `enum CarFluid : ETransportFluid {}` (рефакторинг, совместимо) |

## 6. Гипотезы для эмпирической проверки (тест-сервер 1.30)

`[нужно проверить]` — не закрывается статически:

1. **Инвентарный синк AI-бота после реврайта `dayzplayerinventory.c`.**
   В 1.30 `ProcessInputData` разведён на `ExecuteInventoryCommandServer/Client/Remote` +
   `ValidateInventoryCommandServer`, и `INSTANCETYPE_SERVER`-проверка в валидации
   (`GetInstanceType() == INSTANCETYPE_SERVER`) отделена от `INSTANCETYPE_AI_SERVER`.
   Вопрос: работают ли у `INSTANCETYPE_AI_SERVER`-бота `LocalTakeToDst` (LOCAL,
   `LocationSyncMoveEntity`) и `TakeToDst(SERVER)` так же, как в 1.29? Probe: сценарий
   «лут-подбор ботом» + `botdump` инвентаря до/после.
2. **`CarFluid` наследование.** `enum CarFluid : ETransportFluid {}` — резолвится ли
   `CarFluid.BRAKE` (унаследованный член) в нативе `Fill(CarFluid,float)` на сервере 1.30
   корректно (= BRAKE, не OIL)? Статически совместимо (значения те же), но проверить
   `Fill(CarFluid.BRAKE,…)` → `GetFluidFraction(CarFluid.BRAKE)` после доливки. Probe:
   `spawncar` + ручная доливка BRAKE, замер фракции.

   **Эмпирика (headless, /car repair):** на idle-сервере без клиента/экипажа
   `LeakAll(OIL/BRAKE/FUEL/COOLANT)` и `Fill(FUEL/COOLANT, cap*0.5)` **не меняют**
   `GetFluidFraction(...)` — остаётся `1.0` (проверено и сразу, и через `sleep 5`).
   При этом `SetHealth01` зон/attachments работает. Гипотеза: флюид-менеджер машины
   симулируется per-frame и не коммитит изменения на idle/headless-машине без водителя
   (в живом гейме — `Fill` из заправки/канистры работает, это штатный путь). Следствие:
   headless-гарнесс **не может** проверить «oil/brake долились, fuel/coolant не тронуты»
   — эта часть `/car repair` верифицируется только код-ревью (в `dmCarRepair.Repair` нет
   FUEL/COOLANT) + ручной проверкой в живом клиенте. Остаётся `[нужно подтвердить]` на
   живом клиенте.
3. **`GetHeatIsolation()` после переноса поля в `ItemBaseType`.** Возвращает ли
   `GetHeatIsolation()` прежнее значение на реальных предметах (config `heatIsolation`),
   учитывая кэш `ItemBaseType.m_HeatIsolation` (инициализируется в `itembasetype.c:84`)?
   Бот читает его для сравнения тёплой одежды (`dmAISurvivor.c:1984`). Probe: `botdump`
   теплоизоляции предмета против `CfgVehicles heatIsolation`.

## 7. Существенные развилки и решения (для `docs/decisions.md`)

1. **Верификация 1.30 — по реальному дереву, не по obsolete-тегам.** Теги `[Obsolete("1.30")]`
   в 1.29 — неполный сигнал (не ловят семантику: `CarFluid`-наследование, перенос
   `m_HeatIsolation`, реврайт синка). Действует пока: есть материализованное 1.30-дерево.
2. **Гайд `update130.md` — ненадёжен (~90% не совпало).** Единственное совпадение —
   `VehicleLightsComponent`. Использовать только как чеклист «что проверить».
   Действует пока: нет авторитетного источника.
3. **Бот не требует миграции кода под 1.30** (все сигнатуры живы). Изменения — семантика
   (флюиды, теплоизоляция, инвентарный синк) — закрываются E2E-прогоном (§6), не правкой кода.
   Действует пока: не выявлено фактической регрессии в прогоне.
