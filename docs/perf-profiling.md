# Профайлинг производительности botorama

Метод замера: `dmBotProfiler` (спансы за `#ifdef DM_BOT_PROFILE`), билд `--prod`
(только `DM_BOT_PROFILE`, дебаг-логи выключены), дамп через E2E-op `prof dump` →
`$profile:dmBotorama/profile/profile_*.csv`. Сценарий: `army` 25 ботов (2 враждебные
команды 13v12) вокруг поселения «Новоселки» (Radius 100), 60 с боя.

### Иерархия (по коду, спаны вложенные)

```
Tick (20.5 с, серверный кадр)
└── Bot.Update (20.4 с)
    ├── Intents (9.0 с)
    │   └── Intent.Flank (8.2 с)
    │       └── PathFinder.FindPath → Path.Find (6.5 с A*)
    ├── Vision.LOS.Loop (5.0 с)
    │   └── Vision.LOS (3.8 с райкаст)
    ├── FSM.Update (4.8 с)
    ├── CommandHandler (2.0 с)
    └── Look (0.07 с) — пренебрежимо
```

Итого ~20.5 с CPU на 60 с игрового времени (≈34% одного ядра), 25 ботов.

### Выявленные горячие точки и причины

1. **`Intent.Flank` — валидация кандидата полным A\***. `FindCandidate` зовёт
   `bot.FindPathTo(cand, path)` (полный A* через `m_AIWorld.FindPath`, ~0.23 мс) на
   каждую кандидатную точку свипа (до 2 за тик), хотя нужен лишь снапнутый
   navmesh-поинт. Отсюда 28278 вызовов A* (471/с). Львиная доля `Path.Find`.
2. **`Vision.LOS` — O(боты × враждебные цели) райкастов** (~40 райкастов/с на бота),
   `HasLOS` итерирует все хиты при `sorted=true` (достаточно `hits[0]`).
3. **`FSM.Update` (4.8 с)** — агрегатный тик FSM (переходы + условия + OnUpdate).
4. **`CommandHandler` (2.0 с)** — построение команды движения каждый кадр.
5. **Аномалии**: 205× `MoveTo: нет пути к <6515,2307>` (бот долбится в одну
   недостижимую точку), 214× `Flank: свип исчерпан` (свип без результата → Fail →
   пересоздание → снова свип).

### План оптимизации (итеративный, «мера → фикс → мера»)

- [x] **Opt-1** (главное): `Flank.FindCandidate` — заменить A* на `SampleNavmesh`
  (дёшево), A* оставить только в `RePath` после принятия кандидата. → A* 28278→11.
- [x] **Opt-2**: `Vision.HasLOS` — early-out на `hits[0]`; троттлинг refresh
  high-threat 10→5 Гц. → Vision.LOS −48% от baseline.
- [ ] **Opt-3**: разобрать `FSM.Update` / `CommandHandler` (нужна большая
  гранулярность). CommandHandler — в основном ванильный `super.CommandHandler`
  (симуляция PlayerBase), мало что можно сделать; FSM.Update 0.03 мс/кадр/бот — уже
  дёшево. Дальше — только балансные/структурные правки (см. ниже).
- [ ] **Баг**: `MoveTo: нет пути к <6515,2307>` — бот долбится в одну недостижимую
  точку (backoff/кулдаун). Снизилось 205→92, но не исчезло.

### Остаточные горячие точки (после Opt-1/2) и что с ними

1. **Vision LOS (~4.6 с = 70% Tick)** — райкаст `Vision.LOS` 1.97 с + цикл
   `Vision.LOS.Loop` 2.67 с. Дальше только (а) снижать refresh ниже 5 Гц (баланс),
   (б) событийный LOS («рейкастить, только когда цель/бот сместились»), (в) урезать
   число одновременно отслеживаемых враждебных целей.
2. **Intent.Flank (~1.5 с)** — вариативно по прогонам (0.99–1.5 с); остаточный
   `HasClearLine`-райкаст на кандидата + свип-ретраи.
3. **CommandHandler (~1.0 с)** — в основном ванильный `super.CommandHandler`
   (детерминированная симуляция PlayerBase) — не оптимизируется на нашей стороне.
4. **FSM.Update (~0.85 с)** — 0.03 мс/кадр/бот, уже дёшево.

## Фаза 2 — масштабирование (v3.499–v3.504, 2026-11) — settlement-боты

Цель сменилась: не «прожать бой», а **поднять число ботов** (Expansion держит ~180, мы —
~30 на проде). Сценарий: **40 settlement-ботов, 15 мин жизни**, тайм-серия окон
(`prof clear` → `sleep` → `prof dump` × N), FPS — через `logAverageFps`. История решений —
`docs/decisions.md` (`perf:*`), research по Expansion — `docs/research/expansion-ai-perf.md`.

### Инструментарий замера (наработан в этой фазе)

| Инструмент | Что даёт |
|---|---|
| `logAverageFps = 1` в `serverDZ.cfg` (+ `-doLogs`) | серверный FPS в RPT. **Headless-семантика**: raw loop-FPS в тысячи (idle ≈5500); сравнивать только ОТНОШЕНИЕМ 0-бот/N-бот (~6.8× на 40 ботах), не абсолютом. Прод-сравнимое — только с клиентом-наблюдателем. |
| `dmPerfTelemetry` + op `perfstats` | пер-фрейм mean/max/p95 числа/длины райкастов и числа/объёма сканбоксов |
| `dmPhysicsProbe` | обёртка всех нативных `RaycastRVProxy`/`RaycastRV`/`RayCastBullet`/`SceneGetEntitiesInBox` — телеметрия/гейтинг в одном месте (~35 сайтов → 1 класс) |
| Субспаны `FSM.State.<Name>`/`FSM.Transitions`/`Expl.*` | атрибуция фрейм-спайков к конкретному состоянию/операции (max_ms) |
| Флаг «смерть мозга» (`s_BrainEnabled` + op `brain`) | A/B «мозг есть/нет»: пешки живы, мозг отключён — отделить скрипт от ванильной симуляции |

### Оптимизации (мера → фикс → мера)

| Версия | Изменение | Эффект (40 ботов) |
|---|---|---|
| v3.499 | **round-robin слайсинг** `TickAll` (SLICE=10 ботов/тик, dt-коррекция `×ceil(Count/SLICE)`) | FPS ~800→~3000 (3.7×), мозг ~4× вниз, райкасты/сканбоксы ~4× вниз |
| v3.502 | **врек-скан по POI** (`m_ByLocation` текущего POI вместо глобального ~5.5k) | `Expl.Explore` total −95%, max 19→6 мс |
| v3.504 | **чанкованный выбор здания** (`dmBuildingScanCursor`, бюджет 100 записей/тик) | `Expl.Explore` max 19→1.95 мс (~10×), `Tick` max 38→7 мс |

### Итог и остаточные точки

- FPS 40 ботов: ~800 → ~3000. Спайк `Expl.Explore`: **19 → 1.95 мс** (~10×).
- Остаточный спайк ~2 мс = полный 100-записный бюджет (per-record ~0.02 мс в скрипт-VM);
  твик бюджета — tradeoff (ниже спайк ↔ выше латентность выбора здания, ~1.3 с при 1000 зданий).
  Принято как баланс.
- **Класс сущности — НЕ рычаг**: Expansion использует тот же `PlayerBase`+`CreateObject`;
  разница — в организации тиков (scheduler/LOD/Dormant/дроссель). Дальше — LOD.

### Методика (уроки этой фазы)

- Между прогонами сравнивать **`<span>.max_ms`**, а не `Tick` total: `Tick` смазывается разной
  FSM-активностью ботов (боевой хаос vs чистая Exploration).
- «Мозг есть/нет» (`brain` op) — надёжный способ отделить наш скрипт от ванили.
- Тайм-серия окон (dump+clear каждые ~3 мин) вскрывает дрейф/накопление, невидимый в одном
  агрегатном дампе.
- Скрипт-ошибки (напр. `Cast`-коллизия) всплывают ТОЛЬКО на загрузке сервера — AddonBuilder их
  не ловит; после каждого изменения обязателен smoke с грепом `SCRIPT (E)`.
