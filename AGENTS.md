# botorama — конвенции разработки

## Принцип «человеческой модели» (гайд по сложным задачам)

Сложные математические модели (замкнутые физические формулы, многокомпонентные поправки,
знаковые конвенции) — хрупки и дороги. Простые «модели человеческого решения» (меряем ошибку →
поправляем) — надёжны. Это главный урок баллистики (v3.71–v3.87).

**Пример (ветер → упреждение)**: компенсация ветра через `wind·coef·t` с обучением по
`windPerp·t` пять раз переворачивала знак (v3.71→v3.81) — каждый фикс ломал другой кейс, потому
что знак `windPerp` зависел от направления прицела. Сработало решение «как человек»: геометрическая
поправка «пуля ушла поперёк на X → доверни на X» (`s_LatCorr`), а упреждение — «предскажи, где будет
цель (V·t), и поправь, если промахнулся». Ветер = упреждение с нулевой скоростью: **одна формула на
класс задач**, а не N частных.

**Правила**:
1. Сначала спроси «как это сделал бы человек?» (мерять и поправлять), а не «какая формула?».
2. Предпочитай **замкнутый контур** (измерение ошибки → коррекция с затуханием) открытой физике.
3. Один механизм на класс задач (ветер + упреждение = одна поправка), а не N частных формул.
4. Сложную модель — только если простая показала недостаточность, и только инкрементально.
5. Каждый знак/конвенция в формуле — источник бага; больше одного-двух → модель переусложнена.

**Признаки переусложнения**:
- Знаки переворачиваются туда-сюда между итерациями (v3.71→v3.81).
- Формула зависит от направления/стороны (например `scale = windPerp·t`).
- Ошибку нельзя объяснить «человечески» («пуля ушла вправо → целюсь левее»).

## Документация

## Классификация знаний (куда писать ошибку/факт)

- Ошибка **синтаксиса/движка Enfusion** (тернарник, области видимости, `ref`,
  `JsonSerializer`, `ToLower`) → `docs/codeguide.md`.
- Знание **механики бота DayZ** (спавн/синк/движение/навигация/инвентарь/бой) →
  скилл `dayz-ai-bot` (`.opencode/skills/dayz-ai-bot/SKILL.md`).
- Новая **сигнатура/поведение API** → `docs/research/<домен>.md`.

## Процесс

- Одна атомарная задача = один коммит; на каждое изменение bump `DM_BOTORAMA_VERSION`
  (`cons/3_Game/constants.c`).
- Реализацию делает субагент `dayz-dev`; ревью оркестратора — по чеклисту `codeguide.md`.
- API-исследование — субагент `dayz-research` (пишет только `docs/research/`).
- E2E-тестирование перед фиксацией — субагент `dayz-tester` (сборка/деплой/сервер/сценарии/логи).

## Координация субагентов (топология «звезда» + лимиты)

1. **Все запросы работы идут только через оркестратора.** Субагенты не делегируют друг
   другу: `dayz-tester` не заказывает код у `dayz-dev`, `dayz-research` не дёргает
   тестировщика напрямую. Пробел в возможности → отчёт `BLOCKED: нужен <X>` оркестратору.
2. **Функциональные тесты частичной работы**: `dayz-dev` сдаёт атомарный блок + функциональный
   сценарий (`tools/e2e/` или `$profile`) + список релевантных доменов. `dayz-tester` гоняет
   блок как «частичный» тест.
3. **Гипотезы исследователя**: `dayz-research` помечает `[нужно проверить]`/`[нужно подтвердить]`
   с конкретным эмпирическим вопросом; оркестратор роутит в `dayz-tester` как hypothesis-тикет.
   Нужны probe-«ручки» моста (`spawnobj`/`raycast`/`scanbox`/`botdump`/…) — расширение `dmE2EBridge`.
4. **Каталог локаций** (`tools/e2e/locations.md`): если тестировщику не хватает локации — отчёт
   `gap` оркестратору, **человек** предоставляет координаты, запись добавляется в каталог.
5. **Анти-бесконечный цикл**: бюджет итераций на задачу — ≤3 rework/delegate-цикла, иначе стоп +
   отчёт; список probe-«ручек» фиксируется заранее (dev делает батчем, не на лету); гипотеза —
   один эмпирический прогон (нет ручки → `blocked on handle`, в очередь, не в цикл).

## Модуль `/test` (конвенции каркаса тестов)

- Тест-код (константы, хелперы, сценарии) живёт ТОЛЬКО в `test/` — не в `cons/`/`core/`.
  Слои зеркалят core: `test/3_Game` — низкоуровневое (константы), `test/4_World` — каркас
  + сценарии + хелперы мира, `test/5_Mission` — команды-хендлеры + bootstrap.
- **Кости vs мясо**: родитель `dmTestSuite_TestCase` держит общее (поля `m_Bot`/`m_Player`/
  `m_SpawnDistance`/`m_TestRange`, спавн-хелперы врагов, `CurrentStateName`/`Fmt`/
  `ForwardTarget`/`HorizontalMove`); сценарий — только свои фазы/проверки. `Setup` обязан
  звать `super.Setup(bot, player)`.
- **SpawnDistance** — где спавнится БОТ-тестировщик (от игрока). **GetTestRange** — от бота
  до края зоны, где спавнятся ВРАГИ. Не путать.
- Спавн врагов — только в родителе (`SpawnEnemy`/`SpawnZombie`/`SpawnEnemyNearBot`/
  `SpawnZombieNearBot`); координаты через `SnapToGroundExactly` (строго на землю), НЕ
  `SnapToGroundRelative` (прибавляет `pos[1]` → враг висит в воздухе).
- Параллельные тесты: реестр `dmTestSuite_TestRunner.s_Active` (ленивая чистка
  `SweepFinished`), отмена — `/test cancel all|last`.

## Логирование (обязательно для каждой доработки)

1. **Любая новая логика оснащается логами**, которые помогут разобрать неожиданную
   ситуацию (переход не сработал, событие не наступило, значение не то). Логи —
   через `#ifdef` **на месте вызова**, под правильным DEBUG-доменом
   (`DM_BOT_DEBUG_FSM`/`BODY`/`LOADOUT`/`PAWN`/`BRAIN`/`SPAWN` — полный список в
   `src/cons/4_World/defines.c`); `dmBotLog.Error` — всегда без гейта.
2. **После доработки включить нужный DEBUG-домен** в `defines[]` нужного `src/*/config.cpp`
   (`CfgMods.dmBotorama_*.defines[]`), чтобы лог реально попадал в `serverLog` при тесте.
   Регрессию тестировщик гоняет с `bash tools/build.sh --test` (все event-домены из
   `tools/defines_test.txt`); прод — `--prod` (только `DM_BOT_PROFILE`); дефолт без флага —
   функциональный (defines как закоммичено). На отладку незнакомого бага — включать заранее,
   а не после первого «не работает».

## Рефлексия после ошибки/развилки

После каждой допущенной/найденной ошибки (своей или на ревью субагента) — зафиксировать
её в документации по правилу классификации выше, в формате:

- **Почему произошло** — корневая причина, что именно пропустили при написании/ревью.
- **Как не допустить в следующий раз** — конкретное правило/памятка/пункт чеклиста
  (что проверить, на что обратить внимание).

Цель — «учиться один раз»: та же ошибка не должна повториться в следующей задаче.

**Развилки/решения** (не ошибки) — в `docs/decisions.md` (журнал решений): субагент в
отчёте перечисляет существенные развилки и принятые решения, оркестратор при ревью
фильтрует и ведёт журнал (формат `Решение/Почему/Действует пока`, кап ~15–20 записей).
Субагенты читают `docs/decisions.md` в начале работы, чтобы не выводить известное заново.

## Субагенты

Определения (source of truth) — `.opencode/agent/dayz-dev.md`, `.opencode/agent/dayz-research.md`,
`.opencode/agent/dayz-orchestrator.md`, `.opencode/agent/dayz-tester.md` (дублируются в глобальный
`~/.config/opencode/agent/` для загрузки — держать в синхроне). Скилл `dayz-ai-bot` — `.opencode/skills/dayz-ai-bot/`.

- **`dayz-orchestrator`** — агент по умолчанию (`default_agent` в `opencode.jsonc`): он сам
  не пишет код, а делегирует реализацию `dayz-dev`, исследование — `dayz-research`,
  E2E-тестирование — `dayz-tester`, и делает ревью/рефлексию.
- **`dayz-dev`** — реализует атомарную задачу (код). Пишет тест-сценарий под своё изменение.
- **`dayz-research`** — исследует ванильный/Expansion API, пишет `docs/research/`.
- **`dayz-tester`** — гоняет E2E-цикл (сборка/деплой/сервер/сценарии/логи), отчёт PASS/FAIL
  оркестратору. Не пишет код мода. Source of truth — `docs/ai-testing-guide.md`.
